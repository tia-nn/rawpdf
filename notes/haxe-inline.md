# Haxeの`inline`

`inline`は、関数呼び出しや定数参照を、**コンパイル時に呼び出し先の中身で置き換える**指定。小さな関数を「抽象化のコストなしで」書くための道具であり、速度のために手当たり次第に付けるものではない。

## なぜ知っておく必要があるか

`SyntaxKind.isTrivia()`のような小さな判定や、`abstract`で包んだオフセット・幅の型（統括3.1節）は、トークン1個ごとに呼ばれる。こうした「型を分けるためだけの薄い層」が実行時の関数呼び出しとして残らないようにするのが`inline`の主な用途である。一方で、付けると困る場面もあるため、使いどころの線引きが要る。

## どういう仕組みか

### 置き換えはコンパイル時に行われる

```haxe
// 定義
public inline function isTrivia():Bool return this < 10;
// 呼び出し
if (k.isTrivia()) ...
// 出力されるJS（概形）
if (k < 10) ...
```

`inline`が無いと、`abstract`のメソッドは`SyntaxKind_Impl_.isTrivia(k)`のような静的関数の呼び出しとして出力される。

引数は1回だけ評価されるよう、必要なら一時変数が入る。意味（評価順・副作用）は`inline`の有無で変わらない。

### 付ける場所は3つある

| 書き方 | 意味 |
|---|---|
| `inline function f()` | その関数の呼び出しをすべて展開する |
| `static inline var X = 10;` | 定数。参照箇所に値が埋め込まれる（初期値は定数式でなければならない） |
| `inline f()`（呼び出し側。Haxe 4以降） | その1か所の呼び出しだけ展開する |

### 付けると困ること

- **再帰できない**: 自分自身を呼ぶ関数は展開しきれないので、コンパイルエラーになる
- **オーバーライドできない**: `inline`メソッドはサブクラスで上書きできない
- **スタックトレースから消える**: 展開された関数は呼び出しフレームを持たないため、例外の発生箇所やブレークポイントがわかりにくくなる
- **コードが膨らむ**: 大きな関数を多くの箇所で展開すると、出力JSが大きくなる

### JSターゲットでは効果が限られる

V8などのJSエンジンは、実行時のJITで小さな関数をすでにインライン展開している。そのため、JSに出力する場合、`inline`で速くなる幅は思ったより小さいことが多い。ただし、evalターゲット（`--interp`）はJITを持たないので、開発中のテストは`inline`の有無で速度が変わり得る。

## 使いどころの目安

- **付けてよい**: 数行で終わる`abstract`のメソッド（判定・変換・演算子）、定数（`static inline var`）、「型を分けるためだけ」の薄いラッパー
- **付けない**: 数十行ある関数、再帰する関数、スタックトレースに残したい処理（パーサの`parseXxx`など）、継承で上書きする可能性があるメソッド
- **迷ったら付けない**: 速度目的の`inline`は、ベンチマーク（WBS M6-1）で効果を測ってから足せばよい。付けるのも外すのも、呼び出し側を変えずにできる

## 具体例

`SyntaxKind`の分類ヘルパは「付けてよい」の典型である。

- 中身が比較1〜2回で、1行で済む
- TokenSourceやパーサが、トークンごとに呼ぶ
- 再帰も継承もしない

一方、M2以降のパーサの`parseDictionary()`のような関数は、再帰下降で互いに呼び合い（再帰になり得る）、スタックトレースにも残ってほしいので付けない。
