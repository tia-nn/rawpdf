# 手書きレキサーと最長一致（maximal munch）

レキサー（字句解析器）は、バイト列を先頭から読み、「次のトークンの種類と終わり」を1つずつ決めて返す。手書きのレキサーは「現在位置のカーソル」と「先頭バイトによる分岐」でできている。トークンの終わりは**最長一致**（読めるだけ長く読む）で決める。

## なぜ必要か

パーサ（構文解析器）は「`1 0 obj`」を「Integer, Integer, KwObj」という単位で見たい。バイト単位のままだと、文法の規則を書くたびに「数字が続く間は…」といった処理が混ざる。レキサーがバイト列をトークン列に変換しておけば、パーサは種類だけを見て文法を判断できる。

このプロジェクトでは、パーサ生成系（ANTLR等）を使わずに手で書く（基本設計3.2節）。壊れた入力でも例外を投げずに必ず何かのトークンを返すこと、トリビア（空白・コメント）も含めて全バイトをどれかのトークンに割り当てること（幅不変条件）を、自分で細かく制御するためである。

## どういう仕組みか

### カーソルと1トークンずつの切り出し

レキサーは「次に読むバイトの位置」（カーソル）を1つ持つ。`next()`は呼ばれるたびに次のことをする。

1. カーソルが範囲の終端（`end`）に達していれば`EndOfFile`を返す（何度呼ばれても返し続ける）
2. カーソル位置のバイトを見て、どの種類のトークンが始まるかを決める（先頭バイトでの分岐）
3. その種類の規則に従って、トークンの終わりまでカーソルを進める
4. 「種類・開始位置・終了位置」を返す

```
入力:  1 0 obj
       ^ カーソル
next() → Integer  [0, 1)   カーソルは1へ
next() → Whitespace [1, 2)
next() → Integer  [2, 3)
...
```

**どの分岐でも、カーソルは必ず1バイト以上進む**（`EndOfFile`以外）。これが守られていれば、壊れた入力でも無限ループにならない。知らないバイトに出会ったら`Unknown`として1バイト以上消費する、という「受け皿」を必ず用意する。

### よくある間違い: 判定と前進を1つの式にまとめる

「続く間は進める」ループで、条件の中でカーソルを進める（`while (isX(get(cursor++)))`）と、**条件が偽になったバイトの分まで1つ進みすぎる**。そのバイトは次のトークンの先頭なのに、今のトークンに取り込まれてしまう。

```
入力: " a"   （空白1つの後に a）
条件で前進する書き方: get(1)='a' を見て偽 → でもcursorは2に進んでいる
                    → Whitespace [0, 2) に 'a' が入る（誤り）
正しくは:            Whitespace [0, 1)、続いて Unknown/Regular の 'a'
```

「見る（覗く）」と「進める」を分け、見て条件を満たしたときだけ進める。あわせて、見る前に`cursor < end`を確かめる（範囲外を読まない）。

### 最長一致（maximal munch）

トークンの終わりは「その種類として読めるだけ長く」読んで決める。

- `endobj`を、`end`（キーワードではない）＋`obj`と分けずに、1つのrunとして切り出してから分類する
- `>>`は、`>`が2つではなく1つの`>>`
- `123abc`は、`123`と`abc`ではなく、regular byteが続く限り1つのrunとして切り出す。その後、内容が数値の形でもキーワードでもないので`Unknown`になる

PDFでは、トークンの区切りはwhitespaceかdelimiterだけ（[バイト分類](byte-class.md)）なので、「regular byteが続く限り読む」が最長一致そのものになる。種類の判定（数値か・キーワードか）は、切り出した後で行う。

### バイト列は文字列にしないで比べる

キーワード（`obj`・`endstream`等）や`%PDF-`の判定は、`Bytes.getString`で文字列を切り出して`==`で比べるのではなく、**長さを比べてからバイトを1つずつ比べる**。理由は2つある。

1. **壊れた入力で例外になる**: PDFのバイト列はUTF-8とは限らない（`0x80`〜`0xFF`もregular byte）。`getString(…, UTF8)`は、JSターゲットでは不正なUTF-8に出会うと例外を投げる（`Invalid code point`。evalでは投げずに置換文字になる、とターゲットで挙動が違う）。`%\xFF\x80…`のような入力でレキサーが落ち、error-tolerant要件を破る。2026-11-18に確認
2. **速さ**: `getString`は呼ぶたびに文字列を新しく作り、デコードもする。regular run（数値・キーワード）はPDFで一番多いトークンなので、トークンごとに一時オブジェクトが増える。長さで先に振り分ければ、ほとんどのrunは比較の前に候補から外れる

比べる相手（`"obj"`等）はASCIIなので、「長さが同じで、各バイトが`"obj".charCodeAt(i)`と等しいか」で判定できる。この処理は`%PDF-`の判定とキーワード照合の両方で使うので、補助関数にしておく。

### 先読み（lookahead）

`<`と`<<`、`>`と`>>`のように、1バイト目だけでは種類が決まらないものがある。このときは、カーソルを進めずに次のバイトを覗いて決める。覗く位置が範囲の終端（`end`）以上なら「次のバイトは無い」として扱う。ここで範囲外を読むと、範囲を限った再レキシング（インクリメンタル再パース）とフルパースで結果が変わってしまう。

### エスケープは前から読んで「2バイトまとめて飛ばす」

literal string（`( … )`）の中では`\(`・`\)`が括弧の深さに数えない括弧になる。「`(`に出会ったら1つ手前が`\`かを見る」という後ろ向きの判定は、`\\(`（エスケープされた`\`のあとの、本物の`(`）を誤判定する。手前の`\`自体がエスケープされているかは、さらに手前を見ないとわからず、連続する`\`の個数の偶奇まで数えることになる。

前から読む側で解決する。`\`に出会った時点で、**`\`と次の1バイトを1つの単位として消費する**。すると、ループの先頭で出会う`(`・`)`は、その時点で必ずエスケープされていないものになり、後ろを振り返る必要が無くなる。

```
(a\\(b))   … \\ を1単位で飛ばす → 次の ( は本物 → 深さ2 → )) で0に戻る
(a\(b)     … \( を1単位で飛ばす → ) で深さ0、終端
```

`\ddd`（8進）や`\`＋改行も、深さを数えるだけなら「次の1バイトを飛ばす」で十分（数字・改行は括弧ではない）。`\`がEOF（範囲の終端）の直前にあるときは、飛ばす相手が無いので、未終端として扱う。

一般に「この位置の意味は手前の文脈で決まる」ものは、後ろを振り返らずに、前から読むときの状態（ここでは「直前が未消費の`\`か」）として持つ。状態を持たずに済むよう、まとめて消費するのが上の方法である。

## 具体例

```
<< /Type /Page >>
```

| 位置 | 先頭バイト | 分岐 | トークン |
|---|---|---|---|
| 0 | `<` | 次も`<` | LeftDoubleAngle `[0,2)` |
| 2 | SP | whitespace連続 | Whitespace `[2,3)` |
| 3 | `/` | Name | Name `/Type` `[3,8)` |
| 8 | SP | | Whitespace `[8,9)` |
| 9 | `/` | | Name `/Page` `[9,14)` |
| 14 | SP | | Whitespace `[14,15)` |
| 15 | `>` | 次も`>` | RightDoubleAngle `[15,17)` |
| 17 | （終端） | | EndOfFile `[17,17)` |

すべてのトークンの長さを足すと17＝入力の長さになる（幅不変条件）。

## このプロジェクトでの使われ方

- 基本設計4.2節: 構造モードの分岐の一覧
- 詳細設計6.2節: `Lexer`のAPI（`next()`・`RawToken`）と実装注意（regular runの分類順、キーワード照合）
- WBS M1-3（構造モード）・M1-4（文字列のサブスキャン）・M3-2（stream本体モード）
- 範囲の終端`end`を越えて読まないことは、M5-2の`boundaryDependent`の前提になる（[stream境界キャッシュ](stream-boundary-cache.md)）
