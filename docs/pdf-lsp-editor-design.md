## 1. 目的・位置づけ

PDFバイナリを「テキストとして」編集するためのエディタ体験を提供する最上位パッケージ。依存は下位方向の一方向のみ: `pdf-semantics`に加え、`reparse`の呼び出しと診断型の利用のため`pdf-cst-parser`へも直接依存する（統括ドキュメント2章・3章）。

構成要素は3つ:

1. **投影層**: バイナリ⇔仮想テキスト文書の双方向変換（2章。本パッケージの中核設計）
2. **language server**: 仮想テキスト文書に対してLSP標準機能を提供（4章・5章）
3. **VS Code拡張**: 仮想文書の提供、hexパネル、LSPクライアント（3章）

## 2. 投影層（バイナリ⇔仮想テキスト文書）

**方針: 仮想文書投影**。実ファイルのバイト列は常に真実の源（source of truth）として保持し、エディタに見せるのは投影された仮想テキスト文書とする。stream本体のような非テキストバイトをそのまま見せるlatin1直読み方式は採らない。

### 2.1 投影規則

- **構造部分**: latin1（1バイト=1文字）で恒等投影する。ただし次項の**制御文字エスケープ**だけは別の文字に写す。どちらも1バイト=1 UTF-16単位を保つため、位置変換は「累積シフトの加減算」だけで済む（2.2節）。
- **制御文字エスケープ（フェーズ0で必須と判明。3.4節）**: VS Codeのテキストモデルは、(a) EOLを1種類（LFかCRLF）しか保持できず、読み込み時に混在EOLを正規化しCR単体をCRLFへ変換する、(b) 先頭512バイトにNULがあると"binary"として開くのを拒否する。そのため、次のバイトはUnicode Control Pictures（BMPの1単位）で表示する。
  - NUL（0x00）→ `␀`（U+2400）
  - 主EOL以外のCR → `␍`（U+240D）、主EOL以外のLF → `␊`（U+240A）
  - **主EOL**はファイルを開いた時点で構造部分のEOL出現数から決める（最多の種別。同数ならCRLF→LF→CRの優先順。EOLが無ければLF）。主EOLがCRLFならCRLFはそのまま、LFならLFはそのまま表示する。CR単体が主EOLのファイルは、テキストモデルがCR単体を保持できないため、**CRバイトを`\n`として表示する**（CRLF/LF以外の主EOLはこの写像で表す）。
  - 主EOLは**その文書を開いている間は固定**し、編集で出現数が変わっても再計算しない（再計算すると、編集のたびに表示全体の写像が変わり得るため）。再オープン時に改めて決める。
  - これにより、仮想文書には主EOLの改行だけが現れ、VS Codeの正規化・binary判定が発動しない。
- **stream本体**: プレースホルダ1行（例: `%[stream 34821 bytes]`。正確な表記は未決定事項）に置換する。プレースホルダは**read-only**。中身の閲覧はhexパネル（3.3節）。
- 投影は**セグメント表**`(byteRange ↔ virtualRange)`のソート済み配列として表現し、双方向の位置変換は二分探索で行う。長さが変わる置換はstream本体のみ（制御文字エスケープは1対1で長さが変わらない）なので、セグメント数はstream数のオーダーに収まる。
- **バイナリ濃度の高いliteral string（UTF-16BE文字列等）**: 制御文字エスケープによりNULが`␀`になるため、**開けない問題は解消した**。可読性（UTF-16BE文字列を日本語として表示する等）はv1では仮想文書側で扱わず、hover・inlay hintでデコード値を表示して補う（semanticsのデコード結果を使う）。仮想文書上でのデコード表示は、literal stringのエスケープ（`\\`・`\r`等。UTF-16の片側バイトが`\`・CR・括弧と重なる文字が多い）と逆写像の複雑さからv2の検討事項とする（10章）。

### 2.2 位置変換とLSP position

- LSPのpositionはUTF-16単位の行内オフセット。**latin1投影では1文字=1UTF-16単位が常に成り立つため、行内変換が単純になる**。プレースホルダ文字列もこの性質を壊さない文字（ASCII）に限定する。これは投影規則が守るべき設計制約として明記する。
- バイトオフセット⇔仮想文書position（line/character）の変換のため、仮想文書側の行頭オフセット表を投影時に構築する。**行分割はLSP仕様のEOL定義（`\n`・`\r\n`・`\r`単体のすべてを行区切りとする）と厳密に一致させる**。2.1節の制御文字エスケープにより、仮想文書に現れる改行は主EOLの1種類だけになる（非主EOLは`␍`/`␊`という通常の文字）ため、LSPとVS Codeの行モデルは常に一致する。
- 位置変換表は**仮想文書のテキスト上で**構築する（CR単体が主EOLのファイルでは、バイト列上のCRが仮想文書上の`\n`に対応する）。

### 2.3 編集の逆変換

- 仮想文書上のテキスト編集 → `{ start, deletedLength, insertedBytes }`のバイト編集へ逆変換し、parserの`reparse`へ渡す。挿入テキストの逆写像は、`␀`→0x00、`␍`→0x0D、`␊`→0x0A、改行（VS Codeが主EOLへ正規化済み）→主EOLのバイト列、それ以外のU+0000〜U+00FF→同値の1バイト。ユーザーがControl Pictures文字を入力・貼り付けした場合も同じ規則でNUL・CR・LFになる（非主EOLやNULを意図的に挿入する手段として許容する）。
- **プレースホルダ範囲に交差する編集は拒否する**（エディタ側のread-only装飾＋編集ガード。stream本体の変更はv2のhexパネル編集・専用コマンドの領域とする）。
- **非latin1文字の入力**（ユーザーが日本語等を入力した場合。上記の`␀`・`␍`・`␊`は除く）は**v1では位置を問わず一律拒否する**。入力時のガードに加え、保存経路（3.1節の`writeFile`）でも逆写像できない文字を含む内容は書き込みを拒否する（フェーズ0で、ガードが無いとエンコーディング層で`?`に化けて黙って保存され得ることを確認した。3.4節）。当初検討した「literal string内はUTF-8バイト列として挿入」案は、挿入文字（例:「日」=仮想文書上1文字）とバイト列（3バイト）の対応が2.2節の「1文字=1UTF-16単位」不変条件と矛盾するため不採用とした。整合させるには挿入直後にバイト列から再投影する（入力した文字が3文字の文字化け表示に変わる）しかなく、UXとして正当化できない。UTF-8テキストの挿入支援が必要になった場合は、直接入力ではなく専用コマンド（エスケープ列`\ddd`やhex stringへの変換挿入）として将来提供する（10章）。

### 2.4 不変条件

- **往復性**: 任意のバイト列 → 仮想文書（制御文字エスケープ込み）→ VS Codeのテキストモデル →（無編集）→ バイト列が恒等であること。VS Codeを経由した往復までを不変条件の範囲とする（テキストモデル側の正規化が実際に問題になったため。3.4節）。CSTのロスレス性（パーサ仕様書4.4節の幅不変条件）に投影層の往復性を積み重ねることで、エディタ全体のロスレス保証が成立する。
- 投影セグメント表は常にバイト列全体を漏れなく・重複なく被覆する。

### 2.5 更新パイプライン

```
キー入力（仮想文書のtext edit）
 → 逆変換（byte edit）
 → parser.reparse（局所差し替え、目標10ms以内）
 → semantics.update（eager部分、目標2ms以内）
 → 投影の差分更新
 → 診断配信（デバウンス）
```

- パーサがフルパースへフォールバックした場合（パーサ仕様書2.3.1節・5.5節）のレイテンシは**本パッケージが吸収する**: フォールバックは非同期に実行し、完了までは旧い木＋旧いモデルで各種リクエストに応答する（結果整合）。

## 3. エディタ統合（VS Code）

### 3.1 仮想文書の提供方式

**`FileSystemProvider`で`pdfedit:`スキームの仮想文書を提供し、通常のテキストエディタで開く方式に確定する**（フェーズ0で成立を確認。3.4節）。CustomEditor＋webview方式は、**VS Codeのカスタムエディタが本物のテキストエディタをwebview内にホストできない**（`ms-vscode.hexeditor`が編集UIを自前実装しているのはこの制約のため）ため編集機能の再発明になり、採らない。保存時は逆変換済みのバイト列を実ファイルへ書き戻す。

フェーズ0の検証で確定した実装方針:

- **エンコーディングはプロバイダが握る**: `readFile`は投影済みテキスト（2.1節）を**UTF-8でエンコードして**VS Codeへ渡し、`writeFile`は受け取ったバイト列をUTF-8としてデコードしてから逆写像・逆投影する。VS Code側の`files.encoding`をlatin1に強制する方式は不採用とした。理由: ファイル先頭のBOM（ヘッダ前junkとして実在し得る）による自動判定が言語別`files.encoding`より優先されて内容が破壊されること、非latin1文字が黙って`?`に置換されて保存されること（3.4節）。UTF-8で渡す方式では、ユーザーの`files.encoding`・`autoGuessEncoding`設定の影響を受けないことを確認した。
- **言語別configurationDefaults**: 仮想文書の言語に`files.encoding: utf8`・`files.autoGuessEncoding: false`・`files.trimTrailingWhitespace: false`・`files.insertFinalNewline: false`・`files.trimFinalNewlines: false`・`editor.formatOnSave: false`を既定値として与える。ユーザーのグローバル設定（xrefエントリの"SP LF"を消す`trimTrailingWhitespace: true`等）より優先されることを確認した。ユーザーが言語別設定で明示的に上書きした場合の防御は、保存経路の逆写像検査（2.3節）に委ねる。
- **保存の逆変換**: `writeFile`は全文を受け取るため、2.1節の写像の逆と、プレースホルダの完全一致検査（欠落・改変があれば書き込み拒否）を全文に対して行う。
- **`.pdf`のエディタ関連付け**: `*.pdf`に`priority: default`のカスタムエディタを登録し、解決時に即座に`pdfedit:`の仮想文書を開いて自分のタブを閉じる「リダイレクト」方式とする（Explorerから開く経路で動作を確認）。
- **dirty状態管理・外部変更検知**: 通常のテキストエディタの仕組みがそのまま機能する。外部変更は`watch`＋`onDidChangeFile`で通知すれば、dirtyでない文書は自動で再読み込みされる。

### 3.2 保存とEOL

- 保存はバイト列の書き戻しのみ。フォーマットや正規化は一切行わない（ロスレス）。
- **EOL**: VS Codeのテキストモデルは混在EOLを読み込み時に正規化し、CR単体をCRLFへ変換する（フェーズ0で確認。旧版の「CR単体でも行モデルは破綻しない」という記述は誤りだった）。これは2.1節の制御文字エスケープで回避する: 仮想文書には主EOLの改行しか現れず、非主EOLは`␍`/`␊`として表示される。ユーザーの改行入力は主EOLのバイト列として保存される（CR単体が主EOLのファイルでもCRが入る）ため、編集によるEOL種の混在は進行しない。そのため旧版で予定していた「CR単体EOL使用の警告診断」（本パッケージの診断）は不要となり、削除した。パーサ層の`stream-eol-nonconforming`（`stream`キーワード直後のEOL非準拠）はそのまま残る。

### 3.3 hexパネル

- webviewとして実装。選択中のstreamオブジェクトの本体バイト範囲（semanticsのAPI経由で取得）を16進ダンプ表示する。v1は読み取り専用。

### 3.4 フェーズ0スパイクの検証結果（2026-11-10、VS Code 1.126.0）

判定: **go**（制御文字エスケープを投影規則に加えることが条件。2.1節）。

検証した3方式:

| 方式 | 内容 |
|---|---|
| A | 投影バイト列をそのまま渡し、言語別設定で`files.encoding: iso88591`を強制 |
| B | プロバイダがlatin1→文字列→UTF-8に変換して渡す（エスケープなし） |
| C | Bに制御文字エスケープ（2.1節）を加えたもの（**採用**） |

フィクスチャ別の結果（「無編集保存でバイト一致」を基準とする。VS Codeの設定を初期状態にした場合と、`files.encoding: windows1252`・`autoGuessEncoding`・`trimTrailingWhitespace`・`insertFinalNewline`・`trimFinalNewlines`・`files.eol: \r\n`を有効にした場合とで結果は同一）:

| フィクスチャ | A | B | C |
|---|---|---|---|
| LFのみ（xrefの行末"SP LF"） | ✅ | ✅ | ✅ |
| CRLFのみ | ✅ | ✅ | ✅ |
| 本体LF＋xref CRLFの混在 | ❌ CRLF→LFに正規化 | ❌ 同左 | ✅ |
| CR単体EOL | ❌ CRLFに変換 | ❌ 同左 | ✅ |
| LFファイルのliteral string内にCR生バイト | ❌ 正規化 | ❌ 同左 | ✅ |
| 先頭512バイト以内にNUL（UTF-16BE文字列） | ❌ 開けない（binary判定） | ❌ 同左 | ✅ |
| ヘッダ前にUTF-8 BOM | ❌ BOM判定が優先され内容破壊 | ✅ | ✅ |
| ヘッダ前にUTF-16 BOM | ❌ UTF-16として解釈され内容破壊 | ✅ | ✅ |
| 非latin1文字を入力して保存 | ❌ `?`に化けて黙って保存 | 保存拒否 | 保存拒否 |

方式Cでは全フィクスチャについて、無編集保存・1文字の構造編集・latin1文字の挿入・改行の挿入（主EOLのバイトが入る）・dirty状態の遷移・外部変更の再読み込み・`.pdf`からのリダイレクトが期待どおりに動いた。

未検証（LSP層の実装時に確認する）: 実在PDF・破損PDFコーパスでの往復、プレースホルダの編集ガード、非latin1入力の入力時拒否のUX、Control Pictures文字の表示・検索・コピー＆ペーストの挙動、保存時の衝突（「ファイルの方が新しい」）、大きなファイル。

## 4. LSP機能マッピング（v1）

| LSP機能 | 内容 | 主な情報源 |
|---|---|---|
| textDocument sync | incremental同期。text edit→byte edit逆変換の入口 | 投影層 |
| diagnostics | パーサ診断＋意味診断をマージしてLSP Diagnosticへ変換（バイト範囲→仮想position変換、severity/codeの対応表を持つ） | parser + semantics |
| definition | `n g R` → 対応する`n g obj`ヘッダへジャンプ | semantics（参照解決） |
| references | オブジェクトヘッダ → そのオブジェクトを指す全`R`の列挙 | semantics（`referencesTo`逆参照インデックス。意味解析層へ移管済み） |
| hover | オブジェクト概要（番号・`/Type`・stream実測長・被参照数）、Name/文字列のデコード値表示 | semantics |
| documentSymbol | Revision（Segment）→ IndirectObject（`3 0 obj — /Type /Page`のような要約ラベル）→ 主要dictキー、の階層アウトライン | semantics |
| foldingRange | obj / dict / array / stream / xrefセクション単位の折りたたみ | CST |
| completion | dictキーの補完。文脈（囲むdictの`/Type`・親キー）に応じた静的キー辞書から候補を出す。**候補提示のみで検証はしない**（スキーマ検証は意味解析層v2のため）。`/Type`の値など代表的な名前値の候補も最小限持つ | LSP層保持の静的辞書 + CST文脈 |
| semanticTokens | name / keyword / string / number / comment / reference等をトークン種から直接マッピング | CST |

## 5. サーバ実装方針

- `vscode-languageserver-node`を使用。v1は単一文書・単一プロセス。
- サーバ状態: `{ bytes, SyntaxTree, SemanticModel, ProjectionMap }`の4点セットを1世代として管理し、編集ごとに世代を進める（すべて不変データなので、非同期フォールバック中も旧世代で安全に応答できる）。
- LSP層はパーサ・意味解析層の型を再エクスポートしない。プロトコル境界で必ずLSP型へ変換する。

## 6. 性能目標（暫定値。実測で調整）

- キー入力への同期処理（逆変換＋reparse＋semantics eager＋投影差分）: **合計16ms以内**（フレーム予算。内訳目安はreparse 10ms / semantics 2ms / 残りが投影と変換）。
- 診断配信: 100〜300msのデバウンス。
- 大ファイル: stream置換により**仮想文書サイズは構造部分のバイト数に比例**する（数十MBのPDFでも仮想文書は数百KB程度が典型）。エディタに巨大バッファを渡さないこと自体が投影方式の主要な利点。

## 7. テスト戦略

- **往復性テスト**: 正常・破損コーパス（パーサ側と共有）＋ファジングで「バイト列→仮想文書→バイト列」の恒等性を検証する（2.4節の不変条件）。
- **位置変換のプロパティテスト**: 変換の単調性・全単射性・境界（プレースホルダ両端）の扱い。
- **編集シナリオテスト**: 仮想文書への編集列を与え、逆変換後のバイト列期待値をスナップショット比較する（プレースホルダ交差編集の拒否を含む）。
- **LSP統合テスト**: サーバをin-processで起動し、request/responseをスナップショット化する。
- **拡張のsmoke test**: VS Code拡張のE2E（開く→編集→保存→バイト比較）を最小限自動化する。

## 8. 開発方針・優先順位

0. **フェーズ0: 垂直スパイク（go/no-go判定）** — **完了（2026-11-10、判定go）**: 最小の投影実装で「VS Codeで開く→1文字編集→保存→バイト列が期待どおり」を貫通させ、3.1節の落とし穴（保存時エンコーディング・エディタ関連付け・dirty管理）が解決可能であることを確認した。結果として投影規則に制御文字エスケープが必須と判明し、2.1節・3.1節・3.2節に反映した（詳細は3.4節）。スパイクのフィクスチャ（EOL混在・CR単体・NUL・BOM付きjunk）は7章の拡張smoke testに引き継ぐ。
1. 投影層を単体で完成させる（往復性テストまで）。LSP機能より先。
2. 診断配信を最初のLSP機能として繋ぎ、パイプライン全体（2.5節）を貫通させる。
3. ナビゲーション → 構造表示 → 入力支援の順に追加する（依存する意味解析層の機能が軽い順）。

## 11. v2構想: stream本体のデコード表示・編集（peek）

v1には含めない。v2の「stream本体の編集UI」の具体案として構想のみ記す（2026-11-10時点）。

### 11.1 狙い

v1ではstream本体はプレースホルダ（2.1節）とhexパネル（3.3節）でしか見られない。content streamのようにデコードすればテキストとして読める本体を、プレースホルダの位置からその場で開いて読み・編集できるようにする。

### 11.2 UI

- デコード済みの本体を、別スキームの仮想文書（例: `pdfstream:/path/file.pdf#4-0`。オブジェクト番号・世代番号で識別し、オフセットは使わない）としてFileSystemProviderで提供する。
- 開く導線は**プレースホルダに対する定義へ移動**とする。LSPの`textDocument/definition`が`pdfstream:`のURIを返せば、Alt+F12（定義をここに表示）でpeek、F12で別タブとして開ける（専用コマンド不要）。補助としてCodeLens（「デコードして表示」）も候補。
- peek内は通常のエディタなので編集できる。表示には本文書と同じ投影（latin1＋制御文字エスケープ。2.1節）を使い回す（content stream内の文字列オペランドは任意のバイトを含み得るため）。
- テキストとして開くのは、デコード結果がテキストとして意味を持つもの（content stream等）に限る。画像（DCTDecode等）・フォント等のバイナリはhexパネルへ振り分ける。

### 11.3 段階

1. **読み取り専用のpeek**: FlateDecodeとフィルタなしのstreamのみ。デコードと定義へ移動の経路だけで実現でき、効果が大きい。
2. **編集**: 11.4節の規則が揃ってから。

### 11.4 編集時の規則（課題）

- **再エンコードはロスレスでない**: inflate→deflateは元のバイト列に戻らない。中身が変更されていないstreamは**元のエンコード済みバイト列をそのまま保持**し、変更されたときだけ再エンコードする。
- **`/Length`の更新が必須**: 本パーサは`/Length`を参照しないが（パーサ仕様書4.3節）、一般のPDFビューアは参照するため、本体長が変わったら更新しなければファイルが壊れたのと同じになる。`/Length`が間接参照（`5 0 R`）の場合は別オブジェクトの編集になる（参照先を書き換えるか、直接値に置き換えるかは要決定）。xrefオフセットのずれは通常の編集と同じ扱い（意味解析層の診断）とする。
- **本文書を唯一の正とする**: stream文書の保存は実ファイルへ書かず、**本文書への編集として反映する**（本体バイト・プレースホルダ表示・`/Length`が変わり、本文書がdirtyになる）。実ファイルへの書き込みは本文書の保存時のみ。これにより「1世代」（5章）に含まれる正のデータは本文書のバイト列のまま保てる。
- **本文書側の編集による無効化**: 本文書の編集で対象streamが消えた・壊れた場合、stream文書を閉じる（または無効表示にする）。
- **暗号化PDF**は復号できないため対象外（semanticsの`isEncrypted`）。

### 11.5 他パッケージへの影響

- フィルタのデコード・エンコードは現行スコープ外（パーサ仕様書2.2節）。置き場所は意味解析パッケージが自然（値デコードの延長）。FlateDecodeはNode標準の`zlib`（ブラウザでは`DecompressionStream`/`CompressionStream`）で実装でき、依存追加は不要。
- 対応範囲（`/Filter`の連鎖、`/DecodeParms`のpredictor等）は着手時に決める。

### 11.6 着手前の検証項目

- peek内で編集・保存したときのdirty表示と元に戻すの挙動、保存を本文書への編集に振り替える流れ（フェーズ0と同様の小さなスパイクで確認する）。
