## 1. 目的・位置づけ

PDFを手書きするためのエディターアプリ・language server実装の基盤となる、PDFバイナリを解析するパーサパッケージ。

**リポジトリ構成**: パーサ・意味解析・LSPエディタ拡張は**モノレポ内の独立した3パッケージ**として分離する（pnpm workspaces。物理構成・依存方向のリント強制・バージョニングは`pdf-editor-overview-design.md` 3章参照）。依存方向は下位方向の一方向のみ:

```
パーサパッケージ（本ドキュメント） … 他のどのパッケージにも依存しない
   ↑ 依存
意味解析パッケージ（pdf-semantics-design.md）
   ↑ 依存
LSP・エディタ拡張機能パッケージ（pdf-lsp-editor-design.md）
```

なお`pdf-lsp-editor`は`pdf-semantics`に加え本パッケージへも直接依存する（`reparse`呼び出し・診断型の利用のため。禁止されるのは逆方向の依存のみ。統括ドキュメント2章・3章）。

パーサパッケージはLSP関連の型・パッケージに一切依存せず、単体でビルド・テスト・利用できる状態を維持する。

## 2. 要件

### 2.1 基本要件

- **error-tolerant**: 壊れた・不完全なPDFでもクラッシュせず、可能な限り解析結果を返す。
- **CSTである（ASTではない）**: 空白・コメントなど、意味解釈上は不要な情報も含めて詳細に保持する（ロスレス）。

### 2.2 パーサのスコープ

**ファイル構造のみを対象とする**。具体的には:

- ヘッダ（`%PDF-1.x`、バイナリマーカーコメント）
- indirect object（`n g obj ... endobj`）
- dict / array / name / string（literal・hex）/ number / boolean / null / reference（`n g R`）
- stream境界（`stream` 〜 `endstream`。**stream本体のバイトは不透明として扱い、中身のデコードはしない**）
- classic xref テーブル
- xref stream（PDF 1.5+。バージョン戦略は3章参照。v1では非対応）
- trailer
- startxref
- incremental update（複数のbody/xref/trailerセグメントが1ファイル中に存在するケース）

**スコープ外**: content stream内の演算子列（`Tj`, `re`, `m/l`等）の解析、フィルタ（FlateDecode等）のデコード。将来的に拡張する可能性はあるが、現時点では対象外。

### 2.3 非機能要件

- **インクリメンタル再パースが必要**: エディタでのキー入力ごとに、ファイル全体ではなく編集箇所周辺だけを再パースできること。
- **既存PDFライブラリに依存しない完全新規実装**（pdf.js / pdfium / lopdf 等は参考にはするが、コードとしては流用しない）。

#### 2.3.1 性能目標（暫定値。実装後の実測で調整する）

フルパースとインクリメンタル再パースを分けて目標値を置く。ここでの数値はすべて叩き台であり、ベンチマークによる実測に基づき見直す前提とする。

**フルパース（初回ロード時のみを想定）**

| ファイル規模 | 目標 |
|---|---|
| 〜1MB（典型的な手編集PDF） | 50ms以内 |
| 1〜10MB | 500ms以内 |
| 10〜100MB | 数秒以内（頻度が低いため多少の遅さは許容） |

**インクリメンタル再パース**

- ファイル全体のサイズではなく、**再パース対象ノード（典型的には1つの`IndirectObject`、数KB〜数十KB程度）のサイズにのみ依存する**ことが本設計の狙いであるため、目標もそれに対して置く。
- 目安: 再パース対象ノードが数十KB程度の典型ケースで、キー入力から新しい木が返るまで**10ms以内**（エディタの入力→再描画のフレーム予算内）。
- 数十MB級のstream本体を持つオブジェクトの編集は例外ケースとして切り分ける。stream本体は不透明バイトとして扱われ境界の再走査（`endstream`探索）のみで済み中身の再パースは発生しないため、この設計上の利点が実際に効いているかをベンチマークの確認項目とする。
- 境界不安定によりフルパースへフォールバックした場合（5.5節）、大きなファイルではこの目標は満たせない。フォールバック時のレイテンシはパーサ側では保証せず、**LSP・エディタ拡張機能パッケージ側で非同期実行・デバウンス等により吸収する責務**とする（10ms目標はあくまで局所差し替えが成立したケースに対する目標）。

**メモリ**

- Green木のオーバーヘッドは**stream本体を除いた構造部分のバイト数**の10倍以内を目安とする（巨大streamを持つファイルではトークン密度が極端に低くなり、ファイル全体サイズに対する倍率は指標として機能しないため）。JSではオブジェクト1個が2〜3フィールドでも40〜80バイト程度を消費し、構造部分の平均トークン長は数バイトなので、object-per-tokenの素朴な表現では10〜20倍に達し得る。rust-analyzer等の3〜5倍水準はRustのメモリレイアウトによるものであり、JSでは前提にできない。目安を超える場合の削減手段として、TypedArrayベースのSoA表現（kind列・length列を平行配列で持ち、ノードは配列インデックスで参照する）を設計上の発展先として想定しておく（v1で必須とはしない）。ベンチマークでは「トークンあたりオーバーヘッドバイト数」を計測し、回帰検知の指標とする。

**計測方法**

- 代表ファイルセット（正常PDF・破損PDFそれぞれについて小/中/大の3段階）を用意し、フルパースおよび単一オブジェクト編集の再パースをベンチマークスイートとしてCIに組み込み、閾値からの悪化を回帰として検知できるようにする。

## 3. 技術選定・対応バージョン戦略

### 3.1 実装言語: TypeScript / Node.js

検討した選択肢と却下理由:

| 言語 | 判断 | 理由 |
|---|---|---|
| Rust | 不採用 | 開発者（自分）が習熟していない |
| Python | 不採用 | 実行速度が最も劣り、タグ付きユニオン的な木構造を安全に扱う型システムも弱い |
| C | 不採用 | error-tolerantな実装で境界チェックのミスがそのままクラッシュ（セグフォルト）に直結するリスクが高い |
| Go | 不採用 | 技術的には問題ないが、個人的に好みでない |
| Haxe | 不採用 | エコシステムが薄く、AIによる実装支援も受けにくい |
| **TypeScript** | **採用** | 型安全性、`Buffer`/`Uint8Array`によるゼロコピーのバイナリ操作、LSP公式実装(`vscode-languageserver-node`)を含む厚いエコシステム |

TypeScriptの「Pythonよりはましだが遅い」という懸念は、後述のインクリメンタル再パース（編集箇所周辺のみ再パース）によって緩和される想定。

### 3.2 パーサ生成系ツールは不採用

tree-sitter・PEG/ANTLR等の宣言的パーサジェネレータは採用しない。理由:

- `/Length` を参照せず常にバイト列走査で境界を決める設計（4.3節参照）や、xref破損時の再同期など、文法だけでは表現しづらい回復ロジックが必要。
- これらはほぼ全域で「外部スキャナ」を手書きすることになり、宣言的文法によるメリットが薄い。

→ **手書きの再帰下降パーサ＋手書きバイト単位レキサー**を採用。

### 3.3 対応バージョン戦略

PDFのバージョン差分（1.0〜2.0）を調査した結果、**ファイル構造のCST文法という観点では、バージョン間の差はごくわずか**であることが分かっている。暗号化（1.1〜）、フィルタ（FlateDecode等）、フォント、透明度、タグ付きPDF、JavaScript、デジタル署名等はすべてstream本体・dict値の「意味」に関するもので、意味解釈をしない本パーサの文法には一切影響しない。

文法レベルで影響があるのは、**classic xrefテーブル（1.0〜） vs xref stream/object stream（PDF 1.5〜）** の違いのみ。

そのため、バージョン対応は次の2段階で進める。

- **v1（本ドキュメントの主対象）**: classic xref時代（PDF 1.0〜1.4相当）の文法を完成させる。
  - 含む: ヘッダ、indirect object、dict/array/name/string/number/boolean/null/reference、stream境界、classic xref、trailer、startxref、incremental update（複数セグメント）
  - 含まない: xref stream（`/Type /XRef`）、hybrid file（trailerの`/XRefStm`）、object stream（`/Type /ObjStm`）
  - 暗号化（`/Encrypt`）はどちらの段階でも文法変更が不要（stream/stringを既に不透明バイトとして扱うため）。
- **v2（将来）**: xref stream・object streamへの対応を追加する。object streamは「stream本体は不透明」というスコープと衝突する（object streamを解決するには結局デコードが必要）ため、対応時に改めてスコープを検討する。

## 4. 字句解析（トークナイザ）設計

### 4.1 バイト分類

PDF仕様上、バイトは3種類に分類される（全バージョン共通）。

- **Whitespace（6バイト）**: `NUL(0x00)` `HT(0x09)` `LF(0x0A)` `FF(0x0C)` `CR(0x0D)` `SP(0x20)`
- **Delimiter（10バイト）**: `(` `)` `<` `>` `[` `]` `{` `}` `/` `%`
- **Regular**: 上記16バイト以外のすべて（0x80〜0xFFの高位バイトも含む）

### 4.2 トークナイザの状態遷移

基本ループ（構造モード）は先頭バイトで分岐する。

- whitespace連続 → `Whitespace`トークン
- `%` → 行末（含まず）まで消費して`Comment`トークン
- `(` → **リテラル文字列サブスキャン**: 深さカウンタ方式（エスケープされていない`(`/`)`のみ深さに影響、`\(` `\)` `\\`等はエスケープとして無視）。EOFまで閉じなければEOFで打ち切り「Unterminated」フラグ付きで確定。
- `<` → 1バイト先読み。次も`<`なら`<<`（2バイト）、そうでなければ**16進文字列サブスキャン**（16進文字と空白を`>`まで消費。不正な文字が混じっても打ち切らず`>`まで飲み込む）。
- `>` → 1バイト先読み。次も`>`なら`>>`、単独の`>`は`Unknown`として回復継続。
- `[` `]` `{` `}` → 単純な1バイトトークン
- `/` → **Nameサブスキャン**: `/`込みで1トークン。regular byteを境界まで貪欲消費。`#xx`は解釈しない（意味解釈層の責務）。空Nameも許容。
- それ以外のregular byte → **regular runサブスキャン**: regular byteの最長一致を1トークン候補として切り出し、内容で分類（先頭の符号（高々1個）＋数字＋単一`.`の構成なら`Integer`/`Real`（`1-2`のように符号が中間に現れる列は該当せず`Unknown`）、既知キーワード（`obj` `endobj` `stream` `endstream` `xref` `trailer` `startxref` `true` `false` `null` `R` `n` `f`）とバイト完全一致なら対応キーワード、どちらでもなければ`Unknown`）。**指数表記（`123e5`等）は非対応で、この分類により自然に`Unknown`となる（特別なロジック不要）**。
- **`stream`キーワードを出した直後 → stream本体モード（4.3節）**: レキサー自身が直後のEOLトリビア・stream本体（`StreamBody`）を続けて切り出し、構造モードに戻る。モード切替はパーサの文脈ではなく**レキサーが出したトークン種だけで決まる**（文脈自由）。理由: (a) パーサ主導の切替では、`stream`の時点で先読みバッファ（パーサ詳細設計6.3節）がすでに本体バイトを構造モードで字句解析している場合があり、本体中の`(`がEOFまで飲み込む等の誤りが起きる。(b) 構造モードのWhitespaceは空白を貪欲に消費するため、本体先頭の`0x0A`・`0x00`等までトリビアに取り込んでしまう。(c) 字句解析が文脈自由であれば、範囲を限った再レキシング（5.5節）とフルパースが同じトークン列を作ることを保証しやすい。誤った位置（dictの後以外）に現れた`stream`でも同じく本体として切り出され、パーサはそれを`ErrorNode`に包む。

### 4.3 stream本体の境界決定

**`/Length`は一切参照せず、常に`endstream`バイト列走査で境界を決定する。** 理由: `/Length`は間接参照になり得て解決に他オブジェクトの参照が必要になる（パーサをローカルなバイト走査だけで完結させたい方針と相容れない）ことに加え、宣言値が実体と食い違う壊れたファイルへの耐性を最初から持たせられるため。

なお、ISO 32000上はstreamの範囲は`/Length`が規定するものであり、本方式は仕様の解釈ではなく**堅牢性を優先した意図的な仕様からの逸脱（回復ヒューリスティックの常時適用）**である。この逸脱には実害のあるトレードオフが伴う: 仕様上正しいPDFであっても、stream本体のバイナリ中に偶然「空白＋`endstream`」列が含まれる場合、本来より早い位置で境界を誤認する（このパーサを基盤とするエディタがそのファイルを壊し得る）。これを利用者が検知できるようにするため、**「宣言された`/Length`と実測長との不一致」の診断はv1の必須機能とする**（本節末尾参照）。

アルゴリズム:

1. `stream`キーワード直後のEOLをstream本体（`StreamBody`トークン）のleading triviaとする。トリビアに取り込むのは次の**高々1パターン**に限り、それ以降のバイトは（空白であっても）本体に含める:
   - 直後が`CRLF`または`LF` → そのEOLのみ（仕様準拠）
   - 直後が`CR`単体 → そのCRのみ（`stream-eol-nonconforming`警告）
   - 直後がSP/HTの連続で、その直後にEOLが続く（`stream  \r\n`等、実在する非準拠） → 空白列＋EOL（`stream-eol-nonconforming`警告）
   - 上記いずれでもない（EOLが無い） → トリビアなし。本体は`stream`の直後から始まる（`stream-eol-nonconforming`警告）
2. そこから前方に`endstream`のバイト列を探索する。探索は**レキサーの字句解析範囲の終端（フルパースではEOF、再レキシングでは範囲終端`to`。5.5.1節）までに限る**。範囲を越えて探索すると、`StreamBody`が範囲外まで伸びたことを検出できないため。候補となる出現は、**直後のバイトがwhitespace・delimiterのいずれかであるか、またはEOFであるもの**に限る（`endstreamXYZ`のようにregular byteが後続する出現はキーワードとして成立しないため候補から除外する）。そのうえで、**直前バイトが空白6種のいずれかである最初の出現を優先的に採用する**。
3. 直前バイトの空白条件を満たす出現が見つからない場合は、直前バイト条件を無視した最初の候補（直後バイト条件は満たすもの）を採用する。
4. どちらも見つからず字句解析範囲の終端に達した場合は「Unterminated」として診断情報付きで打ち切る（本体は範囲終端まで）。範囲終端で打ち切られた本体は、5.5.1節の規則により再レキシング結果を必ず「不安定」とする。範囲終端に接する候補（直後バイトが範囲外になるもの）も同様に5.5.1節で扱う。

**stream本体の終端（bodyEnd）の規則**: 採用した`endstream`の直前にEOL（CRLF・LF・CR単体のいずれか）が存在する場合、その**EOL 1つ分を本体に含めない**。ISO 32000はstreamデータ末尾と`endstream`の間にEOLを置くと規定しており、`/Length`はこのEOLを含まないため、含めてしまうと仕様準拠ファイル全件で`/Length`不一致診断（意味解析パッケージ）が誤発火する。除外するEOLは高々1つとし、その手前にさらに空白が連続していてもそれらは本体に含める。除外されたEOLは4.4節の規則により`endstream`トークンのleading triviaとして保持されるため、ロスレス性（幅不変条件）は損なわれない。

**実装上の性能要件**: 数十MB級のstream本体を持つオブジェクトでは、dict部分の1文字編集ごとに本体全域の`endstream`再走査が発生し得る。`Uint8Array`に対する手書きループ（数百MB/s程度）では2.3.1節の10ms予算を超えるため、次の2点を実装要件とする: (a) バイト列探索には`Buffer.indexOf`等のネイティブ実装相当の高速探索を使う（ブラウザ対応時は代替実装を用意）。(b) インクリメンタル再パース時、前回の境界決定結果が変わり得ない場合は再利用し、再走査を省略する。**再利用してよいのは、編集範囲（旧座標の閉区間`[start, start + deletedLength]`。挿入のみなら挿入位置1点）が、閉区間`[streamキーワードの開始, endstreamキーワードの終端]`に接触も交差もしない場合に限る**。本体のバイト範囲だけを見るのでは足りない。境界決定は本体の外側のバイトにも依存するためである:
   - `stream`直後のEOL（本体の開始位置を決める）
   - 本体直後のEOL（`endstream`のleading trivia。消すと「直前が空白」の条件が崩れ、後ろの別の出現が選ばれ得る。bodyEnd規則にも影響する）
   - `endstream`の直後1バイト（`endstreamX`のように書き換えると候補から外れる）。`endstream`キーワードの終端位置（排他的終端）はこの1バイトの位置そのものなので、上の閉区間に含まれる
   - `stream`の直前1バイト（消す・regular byteを挿入すると`stream`がキーワードとして成立しなくなる）

この設計により、**CSTパーサは構造解析中に間接参照を一切解決する必要がない**（`/Length`の参照先を探しに行く処理が丸ごと不要）。「宣言された`/Length`と実測長との不一致」の診断は、上記の境界誤認トレードオフを利用者が検知するための安全網であるため、将来の後付けではなく**v1で実装する**。ただし`/Length`は間接参照になり得て解決には参照解決機構が必要なため、実装先は本パッケージではなく**意味解析パッケージ**（`pdf-semantics-design.md` 3.6節）とする。本パッケージはstream実測長（CSTのバイト範囲）とdictのCSTを提供するのみ。

### 4.4 トリビアの木への付与規則

**トリビアはすべて直後の実トークンのleading triviaとして付与する**（trailing triviaの概念は持たない）。ファイル末尾のトリビア（最後の`%%EOF`コメント等）を受け取る先として、幅ゼロの`EndOfFile`番兵トークンを1つ用意する。

この規則により「Green木の全子要素の幅の合計＝ファイル全体のバイト数」という不変条件が常に厳密に成り立ち（5.5節のインクリメンタル再パースの前提）、かつ次のような副次的な利点がある。

- xrefエントリ内の区切りスペースも特別扱い不要（単に次トークンのleading trivia）。
- `stream`キーワード直後のトリビアの中身を見るだけで、「CR単体は許容するが警告診断（`stream-eol-nonconforming`。本パッケージが発行し、LSP層は変換・配信のみを担う）を出す」が実現できる（トークナイザに専用の状態を追加する必要がない）。
- 想定外の位置に紛れ込んだコメント等も、特別なエラー処理なしに自然に吸収できる。

### 4.5 SyntaxKind一覧（v1ドラフト）

**トリビア**: `Whitespace` / `Comment`（`%%EOF`もこの分類。4.4節の規則によりセグメント境界の`%%EOF`は**次Segment先頭トークン**（ファイル末尾では`EndOfFile`）のleading triviaに現れるため、パーサはそのtrivia内容が`%%EOF`パターンに一致することを見て意味づけするだけで、専用トークンにはしない）

**リーフトークン**:
- `Integer` / `Real`
- `Name`
- `LiteralString` / `HexString`
- `LeftBracket` `[` / `RightBracket` `]`
- `LeftDoubleAngle` `<<` / `RightDoubleAngle` `>>`
- 構造キーワード: `True` `False` `Null` `R` `Obj` `Endobj` `Stream` `Endstream` `Xref` `Trailer` `Startxref` `N` `F`（`N`/`F`はxrefエントリの`n`/`f`。4.2節の既知キーワード一覧と1対1で対応させる）
- `Unknown`（どの分類にも合わないバイト列の受け皿）
- `EndOfFile`（幅ゼロの番兵トークン）

詳細設計（`pdf-cst-parser-detailed-design.md` 1章・3章）での追補: `HeaderMarker`（`%PDF-`コメントは非トリビアの実トークンとする。`Header`ノードが幅を持つため）・`StreamBody`・`LeftBrace`/`RightBrace`を追加し、当初案にあった`Error`トークンは`Unknown`に一本化した（上のリストは一本化を反映済み）。

xrefエントリ（本来は10桁offset＋5桁generation＋`n`/`f`の固定20バイト記録）は、専用の固定長トークン種別を設けず、**通常の`Integer`/`Whitespace`/キーワードトークンの並びとして表現し、妥当性（桁数・区切り数・EOL種別）はパーサが検証する**方式を採用した（5.3節参照）。固定長で機械的に読む方式は、1件のズレが後続全体に連鎖するため、error-tolerance要件と相性が悪いと判断した。

**ノード**:
- `Document`（root）
- `Header`（5.2節。`HeaderMarker`トークンを子に持つ）
- `Segment`
- `IndirectObject`
- `StreamClause`
- `Array` / `Dictionary` / `DictEntry`
- `Reference`
- `XrefSection` / `XrefSubsection` / `XrefEntry`
- `TrailerClause`
- `StartxrefClause`
- `ErrorNode`（回復時に不明なトークン列を包む。`SkippedTokensTrivia`的な位置づけ）

## 5. 文法（パーサ）設計

### 5.1 CST設計: 自前のGreen/Redツリー

Roslyn / rust-analyzer（rowan）と同様の「不変・構造共有されるGreenツリー＋親情報を持つ軽量なRedビュー」という設計を踏襲するが、**rowanをそのまま使わず自前実装する**。

理由: rowanはトークンのテキストをUTF-8前提（`SmolStr`）で保持するため、stream本体やliteral string中の非UTF-8バイナリバイトを扱えない。

代わりに、トークンのテキストは保持せず元バッファへの参照で表現し、デコードは必要になった時点で遅延して行う。バイト範囲の表現は次の役割分担とする:

- **Greenトークン／ノードは`{ kind, length }`のみ（相対長）を保持し、絶対オフセットを持たない**。絶対オフセットを持つと編集のたびに後続全トークンの更新（O(n)）が必要になり、構造共有と5.5節の「オフセットシフトO(深さ)」が成立しなくなるため。
- 絶対オフセット（`start`）は、rootからの累積で計算できる**Redビュー側の計算プロパティ**として提供する（公開APIの`{ kind, start, length }`アクセサはRedビュー上のもの。6章）。

これにより:

- stream本体は1つの不透明トークン（バイト範囲だけ）として扱え、コピーが発生しない。
- literal string中の非UTF-8バイトもそのまま扱える。

### 5.2 トップレベル文法

```
Document := LeadingJunk? Header? Segment+ TrailingJunk?
Segment  := IndirectObject* XrefSection? TrailerClause? StartxrefClause?
```

- `Header`（`%PDF-1.N`）は`Document`直下に1つだけ持つ（`Segment`には含めない）。ISO 32000-1 §7.5.2は「ファイルの先頭行はヘッダでなければならない（shall）」と規定しており、**ヘッダが先頭にあること自体はnormativeな要求である**。一方、「先頭付近（1024バイト以内）にあればよい」という許容はISO 32000の要求事項ではなく、Adobe PDF Reference巻末の「Implementation Notes」付録に記載された、Acrobatビューアという特定の実装が歴史的に持っていた許容挙動（バージョンにより変化あり）に過ぎない。本パーサが`Header`より前に任意のjunkバイト列を文法上許容するのは、仕様がそれを許しているからではなく、**仕様違反ファイルに対するerror-tolerance要件（2.1節）のため**である（junkが存在する場合は診断を付与する）。判定は固定バイト数（1024等）に頼らず、次項の同期トークンベースの方式に委ねる。
- `Header`自体もoptionalとする（欠落時はnull＋診断情報「ヘッダが見つからない」を付与）。2.1節の error-tolerant 要件（壊れた・不完全なPDFでもクラッシュせず、可能な限り解析結果を返す）と整合させるため、xref/trailer/startxref同様、`Header`が見つからない場合でもそれ以降の`Segment+`の解析を継続する。判定方法は、あらかじめ決めたバイト数まで`%PDF-`を探すのではなく、`LeadingJunk`を消費している最中に（5.3節のDocument/Segmentレベルの同期トークン集合と同じ）`Integer Integer obj`パターンや`xref`等、Segmentを開始する既知のトークン列が`%PDF-`より先に現れた場合、その時点で「ヘッダは存在しない」と判定し、そこまでを`LeadingJunk`として確定してSegment解析に移る、という同期トークンベースの方式を採る。これにより`%PDF-`の探索範囲を固定バイト数で区切る必要がなくなる。
- 各`Segment`は「body（indirect objects）→ xref → trailer → startxref」の順で、ファイル中の物理的な出現順が古い revision → 新しい revision の順とそのまま一致するため、並べ替え処理は不要。`/Prev`は普通の`DictEntry`として解析するだけで、意味づけ（どのxrefを指すか）は意味解析パッケージ（`pdf-semantics-design.md` 3.3節のリビジョンモデル）の責務とする。
- xref/trailer/startxrefが読み取れない壊れたファイルでも木を作れるよう、`Segment`内のこれら3つは全てoptional（欠落時はnull＋診断情報）として表現する。
- 複数`Segment`の境界は「直前の`Segment`の後、まだファイル末尾に達していないか」で判定する。
- `Segment`の構成要素は全てoptionalであるため、文法上は空列にもマッチし得る。手書き再帰下降での無限ループを避けるため、**「1トークンも消費できなかった`Segment`は生成せず、その位置のトークンをDocumentレベルのエラー回復（5.3節）に回す」という進捗保証を実装上の不変条件とする**（`Segment+`のループは毎周回で必ず1トークン以上前進する）。
- `LeadingJunk`/`TrailingJunk`は文法説明上のラベルであり、専用のノード種別は設けない（4.5節の一覧にも存在しない）。実体は`ErrorNode`＋`unexpected-token`診断で表現する。また`Segment`内のxref/trailer/startxref欠落時の「診断情報」には専用コード`segment-section-missing`（warning。欠落したセクション種別をdataに持つ）を用いる。

### 5.2.1 `Reference`（`n g R`）のパース戦略

`Integer`が現れた時点では、それが単独の数値なのか、`n g R`（参照）の一部なのか、トップレベルでは`n g obj`（オブジェクトヘッダ）の一部なのかを区別できない。そこで**トリビアを透過して最大2トークン先まで先読みし、`Integer Integer R`／`Integer Integer obj`パターンに完全一致した場合のみ`Reference`／`IndirectObject`ヘッダとして確定する**（一致しなければ単なる`Integer`1つとして消費して次に進む）。バックトラックは行わず、先読み判定のみで決定する。

- 例: `[1 2 R]`は`Reference`1つ、`[1 2 3]`は`Integer`3つ。
- 配列やdict値の途中で`Integer Integer`まで読んだ状態で閉じトークンやEOFに達した場合は、そのまま`Integer`2つとして扱う（部分一致を`Reference`に昇格させない。エラー回復との干渉を避けるため）。
- `1 % comment`＋改行＋`2 R`のように参照の構成トークン間にトリビアが挟まるケースも仕様上は合法であり、先読みがトリビアを透過することで同じ規則で処理される。

### 5.3 エラー回復戦略

**スタックベースの同期トークン集合**によって回復する。単純な固定同期トークンだけだと「スキップし過ぎる（欠落した`endobj`を待って次のオブジェクトまで飲み込む）」「スキップし足りない（内側のルールの同期トークンしか見ておらず、実質ファイルが終わっていることに気付けない）」という失敗が起きるため、各構文規則が自分の同期トークン集合を**スタックに積み**、エラー時は「現在スタックに積まれているどの階層の集合にも一致する」トークンが現れるまで`ErrorNode`に飲み込みながら読み進め、一致した階層まで巻き戻る。

| 階層 | 同期トークン |
|---|---|
| Document/Segment | `Integer Integer obj`パターンの開始、`xref`、`trailer`、`startxref`、`%%EOF`パターンのComment |
| IndirectObject内 | `endobj`（＋上位にエスカレーション） |
| Dictionary内 | `/`、`>>`（＋上位にエスカレーション） |
| Array内 | `]`（＋上位にエスカレーション。有効な同期トークンが乏しいため早期エスカレーションに頼る） |
| Xrefエントリ（1行） | EOLトリビア境界（＋上位が先に現れたらエスカレーション） |

**同期トークン検出の実装上の注意**: 表中の`Integer Integer obj`パターンや`%%EOF`パターンの検出は、単一トークンの照合ではなく、**トリビアを透過した複数トークンの先読み**（`%%EOF`についてはCommentトリビアの内容照合）になる。同期スキャンのループはこの前提で設計する。

**missing tokenの合成**: 閉じ括弧等を待っている最中に純粋にEOFへ到達した場合は、スキップではなく**幅ゼロの合成トークン（missing token）を挿入**して閉じ、「本来あるべきトークンが見つからないままEOFに達した」という診断を残す。この合成はEOF時に限らない: 同期トークンによるエスカレーションで外側の規則に巻き戻る際も、**その時点で未クローズの構文（`>>`が来ないまま次のオブジェクトが始まったDictionary等）にはすべて幅ゼロのmissing tokenを挿入して閉じる**。これにより、どの回復経路を通っても「Green木の全子要素の幅の合計＝ファイル全体のバイト数」（4.4節）という不変条件と木の整形式性が保たれ、欠落トークン診断の表現も一貫する。

**再帰深度の制限**: Dictionary/Arrayの異常なネストによるスタックオーバーフローを避けるため、再帰下降のネスト深さに上限を設け、超えた時点でそれ以上のネストを許可せず`ErrorNode`として平坦に扱う（具体的な上限値は10章の未決定事項）。

### 5.4 ブルートフォース回復レイヤーについて

xref破損時に「ファイル全体を`\d+ \d+ obj`パターンで走査して復元する」という独立したレイヤーは、**v1では別途実装しない**。理由:

- 5.2節の文法により、CSTパーサはxrefテーブルの内容を一切信用せず、ファイルを先頭から素直に辿ってbody中の`IndirectObject`を全部見つける（xrefが壊れていようが存在しまいが、body中に物理的に存在するオブジェクトは通常のトップダウン解析でそのまま見つかる）。
- 5.3節のエラー回復（Document/Segmentレベルの同期トークンに`Integer Integer obj`パターンを含む）により、構造が崩れて再同期が必要になった場合も、「`obj`パターンを探して復帰する」というブルートフォース走査相当の動作をすでに行っている。

残る作業は、論理インデックス（オブジェクト番号→CSTノードの対応表）を作る際に、**xrefの宣言オフセットを鵜呑みにせず、CSTが実際にトップダウンで見つけた`IndirectObject`群を正とする**（食い違いがあれば後者を優先する）というポリシーのみである。論理インデックスの実装はこのポリシーごと意味解析パッケージ（`pdf-semantics-design.md` 3.1節）へ移管した。本パッケージはCSTを提供するのみで、対応表は持たない。

トップダウン解析自体がごく初期段階で壊滅的に破綻するような極端なケースに対する、CSTと独立した「最終手段の生バイトregex走査ツール」は、頻度が低いため将来の拡張として後回しにする。

### 5.5 インクリメンタル再パース

- 各 `n g obj ... endobj` は同期トークンで区切られる自然な最小単位。
- Greenノードは相対長のみ保持するため、差し替え後の後続要素のオフセットシフトはO(深さ)で済む。

#### 5.5.1 再パース対象範囲の特定アルゴリズム（段階的拡大方式）

編集がオブジェクト境界そのものを変化させるケース（例: 編集前は`Unknown`トークン列だった箇所が、編集後に新たな`n g obj`〜`endobj`境界を生成する／逆に既存の`endobj`が編集で消える）に対応するため、tree-sitterのedit+reparseに近い「境界の安定性を検証し、不安定なら範囲を広げる」方式を採る。

1. **候補ノードの特定**: Green木を編集位置 `[start, start + deletedLength)` で走査し、これを包含する最も内側の`IndirectObject`（またはxref/trailer/startxrefセクション）を候補とする。編集位置がノード境界ちょうどに乗っている場合は、隣接ノードも安全側に候補へ含める。編集が既存のSegment同士の境界をまたいでいる、あるいはHeader／LeadingJunk領域にかかっているなど、そもそも単一の候補ノードに包含されない場合は、この段階で直ちにフルパースにフォールバックする（Step 2以降には進まない）。
2. **再レキシング**: 候補ノードのバイト範囲（編集適用後）に対してのみトークナイザを再実行する。
3. **境界の安定性検証**: 再レキシング結果の開始・終了トークンが、変更前と同じ意味的境界（例: 依然として`n g obj`で始まり`endobj`で終わる）を保っているか確認する。
   - 一致 → そのノードだけを新しいサブツリーに差し替えて完了。
   - 不一致（`endobj`が消えた／新たな`obj`パターンが生まれた等） → 候補範囲を1段階外側（親の`Segment`）に広げてStep 2からやり直す。
   - **範囲を越え得るトークンの強制不安定化**: サブ範囲の再レキシングが健全なのは、全トークンのレキシングがその範囲内で完結する場合に限られる。**再レキシングの末尾要素（トークンまたはトリビア）の長さが範囲外のバイトに依存し得る場合は、開始・終了トークンの一致如何にかかわらず必ず「不安定」と判定**して範囲拡大（またはフルパース）に進む。局所再レキシングの結果をそのまま信用してはならない。該当するのは次のすべて（どれも「範囲終端`to`で走査を打ち切らなければ、`to`の位置のバイトを読んで続きを消費していた」ケースとして一律に判定できる）:
     - literal string・hex string・stream本体のような「終端記号が現れるまで消費し続ける」トークンがUnterminated（範囲終端で打ち切り）になった。編集（`(`・`<`の挿入等）によって候補範囲の末尾を突き抜け、本来は後続オブジェクトまで飲み込むケース。
     - regular run（数値・キーワード・`Unknown`）が範囲終端に接して終わり、`to`の位置のバイトがregular byte。範囲で切ったために、本来1つのrunが2つに分かれている（例: 旧`>>1 0 obj`の`>>`を`ab`に書き換えると、フルパースでは`ab1`の1トークンになる）。
     - 単独の`>`（`Unknown`）や`<`で終わり、`to`の位置のバイトと組み合わさって`>>`・`<<`になり得る。
     - コメントが範囲終端に接して終わり、`to`の位置のバイトがEOLでない（コメントが行末まで伸びる）。
     - 範囲末尾にトリビアが残った（最後の実トークンの後ろに空白・コメントがある）。トリビアは次の実トークンのleading triviaになる規則（4.4節）のため、範囲外の次トークンのトリビアと結合されるべきものが範囲内で宙に浮く。
     - stream本体の`endstream`候補が範囲終端に接している（直後バイト条件の判定に`to`の位置のバイトが要る）。
4. **フォールバック**: `Segment`単位まで拡大しても境界が安定しない場合はフルパースにフォールバックする。xref/trailer/startxrefセクション自体への編集も、Step 1の候補ノード（該当セクション）として同じ局所差し替え＋安定性検証の対象であり、フルパースへ直行はしない。v1では「`IndirectObject`→`Segment`の1段階まで拡大し、それでも不安定ならフルパース」という単純な方針から始め、必要が生じた場合に拡大段階を増やす。

将来、より細かい粒度のインクリメンタル性が必要になった場合、同じGreen木構造の上に本格的なtree-sitter的edit+reparseアルゴリズム（トークン単位での差分再利用等）を載せることも可能（現時点ではオブジェクト単位の粒度で十分と判断）。

#### 5.5.2 `reparse` APIの契約

- `reparse`は常に「正しい」完全な木を返すことを保証する。局所的な差し替えが境界不安定により失敗した場合は、内部でフルパースにフォールバックするため、呼び出し側から見た結果の正しさは常に保証される。
- 一方で「どこまで局所的な差し替えで済んだか」というパフォーマンス特性は契約の対象外とし、内部最適化として扱う（LSP側が実際に再パースされた範囲を知りたい場合に返す拡張APIは将来必要になれば追加検討する）。

## 6. 公開インターフェース（意味解析パッケージ向け）

本パッケージが意味解析パッケージ（およびLSP・エディタ拡張機能パッケージ。後者は`reparse`・診断型のため本パッケージへ直接依存する）に提供する必要がある主なAPI（詳細は実装時に確定）:

- `parse(buffer: Uint8Array): SyntaxTree` — 新規パース。Node専用の`Buffer`ではなく`Uint8Array`を受け、ブラウザ環境での利用可能性を残す（`Buffer`は`Uint8Array`のサブクラスであるため、Node側からはそのまま渡せる）
- `reparse(tree: SyntaxTree, edit: { start, deletedLength, insertedBytes }): SyntaxTree` — インクリメンタル再パース
- ノード／トークンのバイト範囲アクセサ（`{ kind, start, length }`。`start`はRedビューが累積計算する値であり、Greenが保持するのは`{ kind, length }`のみ。5.1節）
- Errorノード・診断情報の列挙。ただし本パッケージが出すのは**字句・構文レベルの診断のみ**（欠落トークン、ヘッダ欠落、非準拠EOL等）。`/Length`不一致・参照解決・構造レベルの診断は意味解析パッケージの責務（診断の共通型は本パッケージが定義し、意味解析パッケージが同じ型を使う）
- stream本体ノードのバイト範囲取得（LSP層の投影がプレースホルダ表示・hexパネル取得に使う）

論理インデックス（オブジェクト番号→CSTノードの対応表）は意味解析パッケージへ移管したため、本パッケージのAPIには含まれない（5.4節参照）。

## 7. 開発方針・優先順位

1. **まずCST/トークナイザ（パーサ）を実装する。LSPは後回し。**
2. パーサ単体の検証方法: PDFファイルを読み込んでCSTをテキストダンプするCLIツールを作る（rust-analyzer等で定番の手法）。
   - 出力をスナップショットとして保存し、リグレッションテストに使う。
   - 壊れたPDFを入力してファジングし、「クラッシュせず何らかの木を返すか」を検証する（error-tolerance要件の検証手段）。
3. パーサが安定した後、意味解析パッケージ → LSP・エディタ拡張機能パッケージの順に着手する（統括ドキュメント7章の直列順）。

例外として、統括ドキュメント7章の**フェーズ0（VS Codeエディタ統合の垂直スパイク）**のみ、パーサ本実装の前または並行の最初期に行う（最大の実現可能性リスクを先に検証するため。開発順序の正は統括ドキュメント）。→ 2026-11-10に完了（判定go）。パーサの文法・API設計への変更は不要だった（投影規則の変更のみ。`pdf-lsp-editor-design.md` 3.4節）。

## 9. テスト戦略

- スナップショットテスト（CSTのテキストダンプを保存し、変更を検知する）。
- プロパティベーステスト／ファジングによるパーサの堅牢性検証。プロパティベーステストはfast-check、カバレッジガイド付きファジングはJazzer.js（libFuzzerのNode.js版）を標準とする（統括ドキュメント3章のツールチェーン決定に従う）。
- **`/Length`無視方針の検証**: `/Length`は一切参照しない方針（4.3節）のため、これを裏付けるテストケースを明示的に用意する。
  - `/Length`が実測ストリーム長と一致する・しない・間接参照になっている、の3パターンいずれについても、境界決定が`endstream`バイト列走査のみで行われ、`/Length`の値によって結果が変化しないことをスナップショットで固定する。
- **`endstream`早期一致は既知のトレードオフとして挙動を固定する**: ストリーム本体中に（意図的な破損、あるいはバイナリデータの偶然の一致により）本来の終端より前に「空白＋`endstream`」というバイト列が出現するケースをテストケース・ファジングの両方に含める。4.3節の通り、これは仕様上正しい解釈ではなく`/Length`非参照方式が抱える意図的なトレードオフである。「本来の終端より早く打ち切られること」を期待結果としてスナップショットに固定するのは、それが正しい挙動だからではなく、**この挙動が実装変更で意図せず変わっていないことを検知し、かつこのケースで`/Length`不一致診断（v1必須。実装は意味解析パッケージ側）が必ず発火することを併せて検証するため**である（後者はパッケージ横断の統合テストとして意味解析パッケージ側に置く）。
- **実PDFの破損コーパス収集**: ランダムファジングだけでは発見しにくい「意味のある壊れ方」を補うため、pdf.js / poppler / mutool 等の既存OSS PDFライブラリのテストスイートやissueトラッカーに蓄積されている実在の破損PDFを収集し、回帰用のスナップショットコーパスに組み込む。実装の初期段階から収集を開始し、パーサの安定度に応じて随時追加する。
