# PDF手書きエディタ 全体設計ドキュメント（統括）

最終更新: 2026-11-11（リポジトリ名を`rawpdf`に決定: 3章・8章）
用途: PDF手書きエディタを構成する3パッケージ全体の統括設計。各パッケージの詳細設計はツリー配下の個別ドキュメントに委譲し、本ドキュメントはパッケージ横断の決定事項のみを持つ。今後のAI支援（実装・レビュー）では、まず本ドキュメントを読んでから個別ドキュメントに進むことを想定する。

## 1. プロダクトの目的

PDFバイナリを「手書き」するためのエディタ。壊れたPDFを開いても解析・表示・編集ができ（error-tolerant）、開いて保存しただけではバイト列が1バイトも変わらない（ロスレス）ことを製品レベルの保証とする。

---

## 2. 全体アーキテクチャ

3パッケージの直列依存。データは下から上へ一方向に流れる。

```
                     [ユーザーのキー入力]
                            ↓ text edit
┌─ pdf-lsp-editor ─────────────────────────────────────┐
│  投影層: 仮想テキスト文書 ⇔ バイト列（逆変換）        │
│  language server: LSP機能をエディタへ提供             │
└──────────────┬────────────────────────────────────────┘
               ↓ byte edit                ↑ SemanticModel
┌─ pdf-semantics ───────────────────────────────────────┐
│  論理インデックス・参照解決・リビジョン・文書構造・     │
│  値デコード・意味診断（CSTへの不変オーバーレイ）       │
└──────────────┬────────────────────────────────────────┘
               ↓ reparse                  ↑ SyntaxTree
┌─ pdf-cst-parser ──────────────────────────────────────┐
│  バイト列 → ロスレスCST（Green/Red木）                │
│  インクリメンタル再パース・字句/構文診断               │
└───────────────────────────────────────────────────────┘
```

- 依存は下位方向の一方向のみ。下位パッケージは上位の型を一切知らない。図の矢印はデータの流れであり、呼び出し関係としては`pdf-lsp-editor`が`parser.reparse`（byte edit）と`semantics.update`を直接駆動する（LSP 2.5節）。このため`pdf-lsp-editor`は`pdf-semantics`に加え`pdf-cst-parser`へも直接依存する（禁止されるのは逆方向の依存のみ。3章）。
- LSPプロトコル型が現れるのは`pdf-lsp-editor`のみ。診断の共通型は`pdf-cst-parser`が定義し、上位が共有する。

## 3. リポジトリ構成: モノレポ

**単一リポジトリ＋pnpm workspacesの3パッケージ構成を採用する**（マルチレポは不採用）。

```
rawpdf/
├── docs/                    … 本ドキュメントツリー
├── packages/
│   ├── pdf-cst-parser/
│   ├── pdf-semantics/
│   └── pdf-lsp-editor/
├── corpus/                  … 共有テストコーパス（正常・破損PDF）
└── benchmarks/              … 横断ベンチマーク（CI組み込み）
```

採用理由:

- 直列依存の3パッケージでは、下位のAPI変更が必ず上位に波及する。モノレポならAPI変更・追従修正・統合テスト更新を**1コミット（atomic change）**にでき、個人開発でのマルチレポ運用コスト（npm link・リリース順序・バージョン整合）を丸ごと回避できる。
- 各パッケージの仕様書がすでに前提としている**破損コーパスの共有**（`corpus/`）と**パッケージ横断の統合テスト**（`/Length`不一致診断等）が単一リポジトリで自然に実現できる。
- ドキュメントツリー（本ドキュメント構成）と物理配置が一致する。

マルチレポの利点だった「依存方向の構造的強制」は、モノレポでは次で代替する:

- 各`package.json`の`dependencies`を下位方向のみに限定する（`pdf-cst-parser`は依存ゼロ。`pdf-lsp-editor`は`pdf-semantics`・`pdf-cst-parser`の両方に依存してよい。2章）。
- dependency-cruiser等のリントで逆方向のimportをCIで機械的に禁止する。

**ツールチェーン（全パッケージ共通）**: テストはvitest（スナップショット・bench含む）、ビルドはtscのみ、モジュール形式はESM専用。プロパティテストはfast-check、カバレッジガイド付きファジングはJazzer.jsを標準とする。

**バージョニング**: 3パッケージは常に同一バージョンで一斉リリースするfixedモードとする（独立バージョンは個人開発では管理コストに見合わない）。`pdf-cst-parser`・`pdf-semantics`はnpmパッケージとして公開可能な形を保ち、`pdf-lsp-editor`はVSIX（VS Code拡張）として配布する。

## 4. パッケージ横断の設計原則

各仕様書に散在する原則のうち、全パッケージが守るべきものを正としてここに集約する。

1. **error-tolerant**: どの層も、入力が壊れていても例外・クラッシュで中断しない。解決できないものは「解決不能」という値＋診断で表現する。
2. **ロスレス**: CSTの幅不変条件（パーサ4.4節）× 投影の往復性（LSP 2.4節）の積み重ねで「開いて保存してもバイト不変」を保証する。中間層はバイト列に対して非破壊。
3. **不変スナップショットの世代管理**: `{ bytes, SyntaxTree, SemanticModel, ProjectionMap }`を1世代とし、編集ごとに新世代を作る。すべて不変データであるため、非同期処理中も旧世代で安全に応答できる。
4. **一方向依存**: 2章の通り。診断のLSP変換など「上位にしかできない仕事」を下位に漏らさない。
5. **診断の役割分担**: 同じ事象を複数層で二重報告しない。

| 層 | 担当する診断 |
|---|---|
| pdf-cst-parser | 字句・構文（Unterminated、missing token、ヘッダ欠落、非準拠EOL等） |
| pdf-semantics | 参照・構造・値（dangling、重複定義、xref不整合、`/Length`不一致、page tree循環等） |
| pdf-lsp-editor | 投影・入力起因（非latin1入力の拒否通知等のエディタ利用上の警告）。下位2層の診断のLSP変換と配信 |

6. **遅延評価**: eagerに計算するのは編集ごとに必要な骨格のみ（再パース対象ノード、論理インデックス、投影差分）。残りは初回アクセス時に計算しメモ化する。

## 5. 性能予算の全体配分

キー入力からエディタ応答までの同期処理をフレーム予算**16ms**に収める。各パッケージの目標値はこの配分から導かれている（数値はすべて暫定。ベンチマーク実測で全体を再配分する）。

| 処理 | 担当 | 予算 |
|---|---|---|
| text edit → byte edit 逆変換 | pdf-lsp-editor | 1ms |
| インクリメンタル再パース | pdf-cst-parser | 10ms |
| SemanticModel更新（eager部分） | pdf-semantics | 2ms |
| 投影差分更新・位置変換 | pdf-lsp-editor | 3ms |

- 予算超過が避けられないケース（フルパースフォールバック等）は同期処理から外し、`pdf-lsp-editor`が非同期＋旧世代応答で吸収する（この責務分担は各仕様書に明記済み）。
- 診断配信は予算外（100〜300msデバウンス）。

## 6. 横断テスト戦略

各パッケージ内のテストは個別仕様書に委譲し、ここではリポジトリレベルの仕組みを定める。

- **共有コーパス（`corpus/`）**: 正常・破損PDF（小/中/大）。パーサのスナップショット、意味解析の診断検証、LSPの往復性テストが同じコーパスを使う。実在破損PDF（pdf.js等のOSSテストスイート由来）を随時追加する。
- **パッケージ横断の統合テスト**: 置き場所は上位パッケージ側とする（例: `/Length`不一致診断の統合テストは`pdf-semantics`、編集→保存のE2Eは`pdf-lsp-editor`）。
- **ベンチマーク（`benchmarks/`）**: 5章の予算表を閾値としてCIで回帰検知する。
- **エンドツーエンドのロスレス検証**: 「コーパスの全ファイルを開いて無編集で保存し、バイト一致すること」を最上位の統合テストとしてCIに置く（原則2の直接検証）。

## 7. ロードマップ

**v1**（各仕様書のv1スコープに対応）:

1. `pdf-cst-parser`: classic xref時代の文法のCST＋インクリメンタル再パース（着手済みの主対象）
2. `pdf-semantics`: 論理インデックス・参照解決・リビジョン・文書構造グラフ・値デコード
3. `pdf-lsp-editor`: 投影層 → 診断 → ナビゲーション → 構造表示 → 入力支援の順

開発順序は原則1→2→3の直列とする（下位が安定してから上位に着手。パーサ仕様書7章の方針を全体に拡張）。ただし例外として**フェーズ0: VS Codeエディタ統合の垂直スパイク**を最初に置く。プロジェクト全体で技術的に最も不確実なのはLSP層のエディタ統合（`pdf-lsp-editor-design.md` 3.1節の落とし穴: 保存時エンコーディング・エディタ関連付け・dirty管理）であり、直列順のままでは最大リスクの検証が最後になってしまう。「開く→1文字編集→保存→バイト一致」の最小貫通を**go/no-go判定**として、パーサ本実装の前（または並行の最初期）に行う。

**フェーズ0は2026-11-10に完了し、判定はgo**。ただし、VS Codeのテキストモデルが混在EOLを正規化すること・先頭付近にNULがあるファイルを開けないことが判明し、投影規則に「制御文字エスケープ」（NUL・非主EOLのCR/LFをUnicode Control Picturesで表示。1バイト=1 UTF-16単位は維持）を加えることを条件とした。エンコーディングはVS Codeに任せずプロバイダ側でUTF-8に変換して渡す方式に確定した。詳細は`pdf-lsp-editor-design.md` 2.1節・3.1節・3.4節。次は直列順の1（`pdf-cst-parser`）に進む。

**v2**（主な候補。詳細は各仕様書の未決定事項）: xref stream / object stream対応（パーサ→意味解析へ連鎖）、辞書スキーマ検証、stream本体の編集UI（hexパネル編集、peekでのデコード表示・編集。後者の構想は`pdf-lsp-editor-design.md` 11章。フィルタのデコード／エンコードは意味解析パッケージへの追加となる）、content stream解析。
