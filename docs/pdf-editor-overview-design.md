## 1. プロダクトの目的

PDFバイナリを「手書き」するためのエディタ。壊れたPDFを開いても解析・表示・編集ができ（error-tolerant）、開いて保存しただけではバイト列が1バイトも変わらない（ロスレス）ことを製品レベルの保証とする。

---

## 2. 全体アーキテクチャ

3パッケージの直列依存。データは下から上へ一方向に流れる。

```
                     [ユーザーのキー入力]
                            ↓ text edit
┌─ pdf-lsp-editor ─────────────────────────────────────┐
│  VS Code拡張クライアント（TS。薄い層）                │
│    FileSystemProvider・hexパネル・LSPクライアント     │
│  ─ ─ ─ ─ ─ ─ LSP（JSON-RPC over stdio）─ ─ ─ ─ ─ ─   │
│  language server（Haxe→JS、Node上）                  │
│    投影層: 仮想テキスト文書 ⇔ バイト列（逆変換）      │
│    LSP機能をエディタへ提供                            │
└──────────────┬────────────────────────────────────────┘
               ↓ byte edit                ↑ SemanticModel
┌─ pdf-semantics ───────────────────────────────────────┐
│  論理インデックス・参照解決・リビジョン・文書構造・     │
│  値デコード・意味診断（CSTへの不変オーバーレイ）       │
└──────────────┬────────────────────────────────────────┘
               ↓ reparse                  ↑ SyntaxTree
┌─ pdf-cst-parser ──────────────────────────────────────┐
│  バイト列 → ロスレスCST（Green/Red木）                │
│  インクリメンタル再パース・字句/構文診断               │
└───────────────────────────────────────────────────────┘
```

- 依存は下位方向の一方向のみ。下位パッケージは上位の型を一切知らない。図の矢印はデータの流れであり、呼び出し関係としては`pdf-lsp-editor`が`parser.reparse`（byte edit）と`semantics.update`を直接駆動する（LSP 2.5節）。このため`pdf-lsp-editor`は`pdf-semantics`に加え`pdf-cst-parser`へも直接依存する（禁止されるのは逆方向の依存のみ。3章）。
- LSPプロトコル型が現れるのは`pdf-lsp-editor`のみ。診断の共通型は`pdf-cst-parser`が定義し、上位が共有する。
- **言語の境界はLSPのメッセージだけ**とする（3.1節）。`pdf-cst-parser`・`pdf-semantics`・language server（投影層を含む）はすべてHaxeで書き、1つのプロセス内で直接呼び合う。TSで書くのはVS Code APIでしか書けない部分（クライアント）だけで、クライアントはHaxeのコードをimportしない。VS Code APIの中でパース結果が必要な仕事（`FileSystemProvider`の読み書き、hexパネル）は、カスタムリクエストでサーバーに委譲する（LSP 3.1節・5章）。

## 3. リポジトリ構成: モノレポ

**単一リポジトリの3パッケージ構成を採用する**（マルチレポは不採用）。Haxeのコードはlix（Haxeのバージョンとライブラリをプロジェクトごとに固定するツール）で管理する。npmの道具（lix自身・Jazzer.js・TSのクライアント・VSIXのパッケージング）は、Node.js付属のnpmで管理する。`package.json`はルート（lix・Jazzer.js・ビルドとテストを呼び出すscripts）とクライアント（VS Code拡張のマニフェストを兼ねる）の2つで、npm workspacesでまとめ、ルートで`npm install`を1回実行すれば両方がそろうようにする。旧版のpnpmは、TSのパッケージがクライアント1つになり、依存方向もHaxeのクラスパスで強制するため利点が無くなったうえ、VSIXを作る`vsce`がpnpmの`node_modules`の構造と相性が悪いため、使わない（2026-11-12）。

```
rawpdf/
├── docs/                    … 本ドキュメントツリー
├── .haxerc / haxe_libraries/ … lix: Haxeのバージョンとライブラリの固定
├── packages/
│   ├── pdf-cst-parser/      … Haxe（ターゲット非依存）
│   ├── pdf-semantics/       … Haxe（ターゲット非依存）
│   └── pdf-lsp-editor/
│       ├── server/          … Haxe（→JS、Node上で動くlanguage server。投影層を含む）
│       └── client/          … TS（VS Code拡張。npm workspacesのパッケージ）
├── corpus/                  … 共有テストコーパス（正常・破損PDF）
└── benchmarks/              … 横断ベンチマーク（CI組み込み）
```

採用理由:

- 直列依存の3パッケージでは、下位のAPI変更が必ず上位に波及する。モノレポならAPI変更・追従修正・統合テスト更新を**1コミット（atomic change）**にでき、個人開発でのマルチレポ運用コスト（npm link・リリース順序・バージョン整合）を丸ごと回避できる。
- 各パッケージの仕様書がすでに前提としている**破損コーパスの共有**（`corpus/`）と**パッケージ横断の統合テスト**（`/Length`不一致診断等）が単一リポジトリで自然に実現できる。
- ドキュメントツリー（本ドキュメント構成）と物理配置が一致する。

マルチレポの利点だった「依存方向の構造的強制」は、モノレポでは次で代替する:

- **クラスパスで強制する**: 各Haxeパッケージのビルド定義（`.hxml`）には、自分の`src/`と下位パッケージの`src/`だけを`-cp`（クラスパス）に入れる（`pdf-cst-parser`は自分のみ。`pdf-lsp-editor/server`は`pdf-semantics`・`pdf-cst-parser`の両方を入れてよい。2章）。テストも同じクラスパスでビルドするため、逆方向の`import`はコンパイルエラーになり、リントを別に用意しなくても機械的に禁止できる。
- クライアント（TS）はHaxeのコードを一切importしない（2章）。

**ツールチェーン（全パッケージ共通）**:

- **言語**: Haxe 4.3.7（lixで固定）。Haxe 5（コルーチンを含む）が安定版になったら移行を検討する（8章）。
- **ターゲット非依存のコア**: `pdf-cst-parser`・`pdf-semantics`、およびサーバーのうち投影層とLSP機能のロジックは、どのターゲットでも動く純Haxe（標準ライブラリの`haxe.io.Bytes`・`haxe.ds.*`等）で書く。`js.*`パッケージ・`untyped`・ターゲット別の条件コンパイル（`#if js`）は、サーバーのI/O層（JSON-RPCのトランスポート・ファイル入出力・タイマー）と、性能上の理由で明示的に許可した少数の関数（パーサ基本設計4.3節の高速バイト列探索）に限る。将来のネイティブ化（HashLink/C++。8章）と、速いターゲットでのテスト実行の余地を残すためである。
- **出力**: language serverはHaxe→JS（ES6クラス出力）の単一ファイルにし、Node上で動かす。CSTダンプ等のCLIも同じくJSに出力してNodeで動かす。
- **クライアント**: TS＋tsc（ESM）。VSIXのバンドル方針は8章。
- **テスト**: utest（Haxeの単体テストライブラリ）。スナップショット比較とプロパティベーステスト（ランダム入力の生成器）は、小さな自作ヘルパーで行う（Haxeには定番のライブラリが無いため。仕組み自体が学習対象でもある）。テストはNodeターゲット（本番と同じ実行環境）で回すことを正とし、ターゲット非依存のコアは開発中の高速な反復のためにevalターゲット（`--interp`）でも回せるようにしておく。
- **ベンチマーク**: Nodeターゲットで計測する（5章の予算は本番の実行環境での値として扱う）。計時は自作の小さなハーネスで行う。
- **ファジング**: Jazzer.jsで、Haxeが出力したJSに対してカバレッジガイド付きファジングを行う。

**バージョニング**: 3パッケージは常に同一バージョンで一斉リリースするfixedモードとする（独立バージョンは個人開発では管理コストに見合わない）。配布物は`pdf-lsp-editor`のVSIX（VS Code拡張）だけとし、`pdf-cst-parser`・`pdf-semantics`は当面リポジトリ内のHaxeライブラリとして扱う（npmへの公開はしない。haxelibへの公開は将来の検討事項。8章）。

### 3.1 実装言語の選定（2026-11-12決定）

旧版ではTypeScriptを全パッケージの実装言語としていたが、**パーサ・意味解析・language serverをHaxeに変更する**。VS Code拡張のクライアントだけはTSのまま残す。

- **理由**: 本プロジェクトは趣味であり、書いていて面白いことを重視する。Haxeの`enum abstract`（`SyntaxKind`）・`abstract`（オフセットや幅など、中身は同じ`Int`だが混ぜてはいけない値の区別）・代数的データ型の`enum`とパターンマッチ（`PdfValue`等）は、本設計の型と相性が良い。
- **言語の境界をLSPのメッセージだけにする理由**: HaxeのコードをTSから呼ぶ方向（ESMでの出力・`.d.ts`の生成・ビルドを分けたときのクラス重複）は道具も前例も少ない。サーバーまでHaxeで書けば、HaxeとTSの境界はLSPのJSON（標準メッセージと少数のカスタムリクエスト）だけになり、この問題自体が無くなる。
- **サーバーをNode上で動かす理由**: VSIXが1つで済む（プラットフォーム別のバイナリが要らない）。vshaxeの`language-server-protocol-haxe`（LSPの型定義）と`vscode-json-rpc`（Node用のトランスポート）をそのまま使える。ネイティブ化（HashLink/C++）は、コアをターゲット非依存に保つことで後から選べる（8章）。
- **非同期処理**: Haxe 4.3には`async`/`await`もコルーチンも無い。パーサ・意味解析・投影は同期的な純関数と不変データとして設計済みであり、非同期が要るのはサーバーのI/O層（リクエストの受信ループ、フルパースへのフォールバック、診断のデバウンス）だけである。この層はコールバックで書き、Haxe 5のコルーチンが安定したら置き換えを検討する。
- **詳細設計の型表記**: パーサ・意味解析の詳細設計の型定義とシグネチャは、**TS風の表記のまま残し、言語中立の擬似表記として読む**。Haxeへの読み替えの規則はパーサ詳細設計0章にまとめる。
- **フェーズ0の結果は有効**: フェーズ0のスパイク（TSで実施）で確かめたのはVS Codeの振る舞い（テキストモデルの正規化・エンコーディング・エディタ関連付け）であり、実装言語に依存しない。ただし`FileSystemProvider`の処理をサーバーへ委譲する構成（LSP 3.1節）は新しい経路なので、L層の最初に小さく検証する（LSP 8章）。

## 4. パッケージ横断の設計原則

各仕様書に散在する原則のうち、全パッケージが守るべきものを正としてここに集約する。

1. **error-tolerant**: どの層も、入力が壊れていても例外・クラッシュで中断しない。解決できないものは「解決不能」という値＋診断で表現する。
2. **ロスレス**: CSTの幅不変条件（パーサ4.4節）× 投影の往復性（LSP 2.4節）の積み重ねで「開いて保存してもバイト不変」を保証する。中間層はバイト列に対して非破壊。
3. **不変スナップショットの世代管理**: `{ bytes, SyntaxTree, SemanticModel, ProjectionMap }`を1世代とし、編集ごとに新世代を作る。すべて不変データであるため、非同期処理中も旧世代で安全に応答できる。
4. **一方向依存**: 2章の通り。診断のLSP変換など「上位にしかできない仕事」を下位に漏らさない。
5. **診断の役割分担**: 同じ事象を複数層で二重報告しない。

| 層 | 担当する診断 |
|---|---|
| pdf-cst-parser | 字句・構文（Unterminated、missing token、ヘッダ欠落、非準拠EOL等） |
| pdf-semantics | 参照・構造・値（dangling、重複定義、xref不整合、`/Length`不一致、page tree循環等） |
| pdf-lsp-editor | 投影・入力起因（非latin1入力の拒否通知等のエディタ利用上の警告）。下位2層の診断のLSP変換と配信 |

6. **遅延評価**: eagerに計算するのは編集ごとに必要な骨格のみ（再パース対象ノード、論理インデックス、投影差分）。残りは初回アクセス時に計算しメモ化する。

## 5. 性能予算の全体配分

キー入力からエディタ応答までの同期処理をフレーム予算**16ms**に収める。各パッケージの目標値はこの配分から導かれている（数値はすべて暫定。ベンチマーク実測で全体を再配分する）。

| 処理 | 担当 | 予算 |
|---|---|---|
| text edit → byte edit 逆変換 | pdf-lsp-editor | 1ms |
| インクリメンタル再パース | pdf-cst-parser | 10ms |
| SemanticModel更新（eager部分） | pdf-semantics | 2ms |
| 投影差分更新・位置変換 | pdf-lsp-editor | 3ms |

- 予算超過が避けられないケース（フルパースフォールバック等）は同期処理から外し、`pdf-lsp-editor`が非同期＋旧世代応答で吸収する（この責務分担は各仕様書に明記済み）。
- 診断配信は予算外（100〜300msデバウンス）。
- 表の処理はすべてlanguage serverのプロセス内で行う（投影層もサーバー側。3.1節）。クライアントとサーバー間のプロセス間通信は予算外とする（テキスト編集の通知はLSP標準のincremental同期で、VS Codeの表示はサーバーの応答を待たない）。ファイルを開くとき・保存するときのカスタムリクエスト（LSP 3.1節）は、キー入力ごとの処理ではないため予算の対象外とする。
- 予算はNodeターゲットでの値とする（Haxeが出力したJSを計測する。3章）。

## 6. 横断テスト戦略

各パッケージ内のテストは個別仕様書に委譲し、ここではリポジトリレベルの仕組みを定める。

- **共有コーパス（`corpus/`）**: 正常・破損PDF（小/中/大）。パーサのスナップショット、意味解析の診断検証、LSPの往復性テストが同じコーパスを使う。実在破損PDF（pdf.js等のOSSテストスイート由来）を随時追加する。
- **パッケージ横断の統合テスト**: 置き場所は上位パッケージ側とする（例: `/Length`不一致診断の統合テストは`pdf-semantics`、編集→保存のE2Eは`pdf-lsp-editor`）。
- **ベンチマーク（`benchmarks/`）**: 5章の予算表を閾値としてCIで回帰検知する。
- **エンドツーエンドのロスレス検証**: 「コーパスの全ファイルを開いて無編集で保存し、バイト一致すること」を最上位の統合テストとしてCIに置く（原則2の直接検証）。

## 7. ロードマップ

**v1**（各仕様書のv1スコープに対応）:

1. `pdf-cst-parser`: classic xref時代の文法のCST＋インクリメンタル再パース（着手済みの主対象）
2. `pdf-semantics`: 論理インデックス・参照解決・リビジョン・文書構造グラフ・値デコード
3. `pdf-lsp-editor`: 投影層 → 診断 → ナビゲーション → 構造表示 → 入力支援の順

開発順序は原則1→2→3の直列とする（下位が安定してから上位に着手。パーサ仕様書7章の方針を全体に拡張）。ただし例外として**フェーズ0: VS Codeエディタ統合の垂直スパイク**を最初に置く。プロジェクト全体で技術的に最も不確実なのはLSP層のエディタ統合（`pdf-lsp-editor-design.md` 3.1節の落とし穴: 保存時エンコーディング・エディタ関連付け・dirty管理）であり、直列順のままでは最大リスクの検証が最後になってしまう。「開く→1文字編集→保存→バイト一致」の最小貫通を**go/no-go判定**として、パーサ本実装の前（または並行の最初期）に行う。

**フェーズ0は2026-11-10に完了し、判定はgo**。ただし、VS Codeのテキストモデルが混在EOLを正規化すること・先頭付近にNULがあるファイルを開けないことが判明し、投影規則に「制御文字エスケープ」（NUL・非主EOLのCR/LFをUnicode Control Picturesで表示。1バイト=1 UTF-16単位は維持）を加えることを条件とした。エンコーディングはVS Codeに任せずプロバイダ側でUTF-8に変換して渡す方式に確定した。詳細は`pdf-lsp-editor-design.md` 2.1節・3.1節・3.4節。次は直列順の1（`pdf-cst-parser`）に進む。

**実装言語の変更（2026-11-12）**: パーサ着手の直前に、実装言語をHaxeに変更した（3.1節）。開発順序は変えない。M0（リポジトリ基盤）をHaxe用に組み直してから`pdf-cst-parser`に進む（`docs/wbs.md`）。

**v2**（主な候補。詳細は各仕様書の未決定事項）: xref stream / object stream対応（パーサ→意味解析へ連鎖）、辞書スキーマ検証、stream本体の編集UI（hexパネル編集、peekでのデコード表示・編集。後者の構想は`pdf-lsp-editor-design.md` 11章。フィルタのデコード／エンコードは意味解析パッケージへの追加となる）、content stream解析。
