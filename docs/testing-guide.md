# ユニットテストの書き方ガイド

最終更新: 2026-11-19（根拠にしてよいものをリファレンス・publicなメンバーのdocコメント・ISO 32000-2に限り、設計書を外した。docコメントを根拠にするときの決まりを足した: 3.1節・5章）。2026-11-19（新設。ユニットテストをClaudeが書く運用に合わせて、役割分担・期待値の決め方・ケースの書き方・形・運用を定めた: 1〜5章、未決事項: 6章）
上位ドキュメント: `pdf-editor-overview-design.md`（統括6章 横断テスト戦略）。テストの置き場所・道具は各パッケージの詳細設計（パーサ詳細設計10章など）。食い違いがあれば上位ドキュメントが正
用途: ユニットテストのケースをClaude（AI）が書き、人間がレビューする運用のための決まり。**人間が実装のコードを読まなくても、期待値が仕様どおりかを判断できる**テストにすることを目的とする

**対象はユニットテストだけ**。スナップショットテストとプロパティテスト（不変条件の一覧、生成器、スナップショットの承認の決まり、テキスト形式のテストを採るか）は、M1-10で基盤を作るときにこの文書に追記する。プロパティテストで確かめる不変条件の候補: 例外を投げない、幅不変条件、`next()`が`EndOfFile`以外で必ず1バイト以上進む、範囲の終端で`EndOfFile`を返し続ける、reparse等価（パーサ詳細設計10章）。

## 1. 役割分担

| 人間が持つ | Claudeが書く |
|---|---|
| 仕様（`docs/`の表・規則）。テストが仕様の穴を見つけたら、仕様を決めるのは人間 | テストケース（表の行） |
| テストの枠組み（比較ヘルパー、表の型） | 観点の表（3.3節）を埋めた境界ケースの洗い出し |

- Claudeは枠組みを変える必要があると考えたら、変えずに提案する
- テストが実装のバグを見つけたら、Claudeは実装を直さずに報告する（失敗するテストはそのまま残してよい。どう扱うかは人間が決める）

## 2. 期待値の決め方

**実装を走らせた結果を期待値として貼らない**。そうすると、テストは仕様ではなく今の実装を写したものになり、実装のバグを固定してしまう。

- 期待値は、ケースの根拠（3.1節）に挙げた仕様の記述から導く
- 仕様から期待値が1つに決まらないケースは、テストを書く前に未決事項として人間に挙げる。決まったら、人間がリファレンスかdocコメントに書く（リファレンスは利用者が読む文書なので、未決事項の一覧は置かない。置き場所は設計書）
- 後のタスクで振る舞いが変わる部分は、期待値を決め打ちしない。位置だけを見るなど、確かめる範囲を狭める（例: `LexerTest`の`anyAt`・`prefix`）

## 3. テストケースの書き方

### 3.1 根拠を書く

各ケースに、期待値の出どころを書く。レビューでは「この行は仕様のどの記述から来たか」を確かめるだけで済むようにする。根拠を書けないケースは、仕様に穴がある合図として扱う（2章）。

根拠にしてよいのは次の3つだけ。

- **リファレンス**（`docs/reference/`）の章・表の行。例: `[Lexerリファレンス1章 HeaderMarker]`
- **publicなメンバーのdocコメント**。型名とメンバー名で指し、行番号は使わない。例: `[TokenFlags.hasのdocコメント]`
- **ISO 32000-2の節**（PDFの仕様そのものから決まるとき）

**設計書（`docs/`直下の基本設計・詳細設計）は根拠にしない**。設計書は実装を書き起こすための作業用の文書で、完成後は更新しないため（統括設計「設計書とリファレンス」）。設計書にしか書かれていない振る舞いをテストしたいときは、先にリファレンスかdocコメントに書くよう提案する（書くのは人間。1章）。

docコメントを根拠にするときの決まり:

- 契約（何をするか、境界でどうなるか: `null`・空・範囲外・終端など）を書いたdocコメントだけを根拠にする。実装の手順をなぞった説明は根拠にならない（それをもとにしたテストは、実装を写したものになる。2章）
- `private`なメンバーのdocコメントは根拠にしない（4.2節）
- docコメントから期待値が1つに決まらなければ、テストを書く前にdocコメントを直すよう提案する

### 3.2 名前

- 「条件 → 結果」の1文にする。例: 「範囲の終端が`>>`の間 → 単独の`>`（Unknown）」
- 1つのケースでは1つの性質だけを確かめる。複数の性質を確かめたいときはケースを分ける
- 失敗したときのメッセージに名前が出るようにする（表駆動では行番号でケースを特定できないため）

### 3.3 観点の表

対象（トークンの種類、構文要素、診断など）ごとに、次の観点を埋める。当てはまらない観点は「該当なし」と理由を書く。人間は、抜けている欄だけを見ればよい。

| 観点 | 例（Lexer） |
|---|---|
| 正常 | 仕様書の表の「例」の列をすべて |
| 境目（最長一致） | 隣に空白・delimiter・regular byteが来たときにどこで切れるか |
| 範囲の端 | 入力の末尾、`end`で途中が切れる、`start`から読み始める |
| 空・最小 | 空入力、1バイトの入力 |
| 不正なバイト | 0x80以上、UTF-8として不正な並び、想定外の文字 |
| 大きさ | 長い入力でもスタックがあふれない |
| 仕様の細則 | 大文字・小文字、前方一致でないこと、など仕様書が明記している規則 |

## 4. テストの形

### 4.1 表駆動

ユニットテストは、節ごとの表（1行＝1ケース）と、それを実行・比較する関数に分ける。例は`packages/pdf-cst-parser/tests/rawpdf/cst/lex/LexerTest.hx`（`LexCase`・`tok`・`whole`・`check`）。

- 表の行には、入力・期待値・名前・根拠だけを書く。分岐やループで期待値を計算しない（同じ形のケースを列挙するための`for`は使ってよい）
- 期待値はできるだけ省略しない。後のタスクで変わる部分だけを省略し（2章）、省略した理由を名前かコメントに書く

### 4.2 公開APIだけをテストする

テストは、クラス・モジュールの公開API（`public`なメンバー）の振る舞いだけを確かめる。`private`なメソッドや内部の状態（例: `Lexer`の`cursor`）は直接テストしない。`@:access`で`private`に触ることもしない。

- 理由: 仕様が決めているのは公開APIの振る舞いで、`private`な部分には期待値の根拠になる仕様が無い（2章）。また、実装の詳細をテストに持ち込むと、振る舞いを変えないリファクタのたびにテストも書き直すことになる
- `private`な処理を直接確かめたくなったら、まず公開APIから入力を届けられないかを考える（例: `Lexer.classifyNumber`は`next()`に`"1.2."`を渡せば届く）
- 公開APIから届けにくいほど複雑な処理は、別のモジュールに切り出し、その公開APIとしてテストする。テストしたくなるほどの中身があることは、独立した部品になっている合図として扱う（候補: パーサ基本設計4.3節の`findEndstream`）
- 切り出すかどうかは設計の変更なので、Claudeは切り出さずに提案する（1章）

## 5. 運用

- Claudeが書いたテストは、実装とは別のコミットにする
- PRでは、どのテストをClaudeが書いたかがコミットからわかるようにする
- レビューでは、ケースの根拠（3.1節）と期待値の導き方（2章）が守られているか、観点の表（3.3節）に抜けがないかを見る（CLAUDE.md「PRレビュー」観点4）
- テストの根拠になっているリファレンスやdocコメントが変わったら、仕様の変更として扱う。docコメントの変更はコードの差分に埋もれやすいので、レビューで意識して確かめる（CLAUDE.md「PRレビュー」観点2）
